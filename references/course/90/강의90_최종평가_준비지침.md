# [최종 평가] 저장소 준비 지침

> 강의 덱 "LLMOps와 LLM 애플리케이션 보안"에서 다룬 운영 기록, 품질 개선, 보안을 저장소에 남기는 최소한의 작업을 정한다.
> 새로 만드는 파일은 추적 기록(`trace.jsonl`)뿐이다. 나머지는 강의 7까지 만든 파일(평가 세트, 러너, `history.csv`, `ARCHITECTURE.md`)에 내용을 더한다. `history.csv`는 강의 7의 열을 그대로 쓰되, `change` 열이 없는 팀은 이 열을 추가하고, 모든 팀이 지표 열로 `attack_success_rate`(공격 성공률)를 추가한다.

## 용어

- **운영 기록**: 제품을 사용하는 동안 요청마다 남기는 추적 기록과, 그 기록에서 찾은 실패를 평가 케이스로 옮긴 결과. 저장소의 다음 파일에 담긴다
  - `logs/trace.jsonl`: 요청마다 한 줄의 추적 기록
  - `evals/evalset.jsonl`: 추적 기록에서 옮긴 실패 케이스(`note`에 출처 요청 id)
  - `evals/results/history.csv`와 결과 파일: 케이스를 추가한 뒤의 측정
  - 실사용자가 없는 이 과목에서는 지금부터의 팀원 사용, 시연, 시나리오 실행을 실사용으로 본다
- **추적 기록(trace)**: 요청 하나가 처리되는 동안의 단계별 실행 결과(입력, 중간 결과, 출력, 버전, 지연, 오류)를 묶은 기록
- **개선 회차**: 가설 하나를 검증하는 수정과 그 전후 측정을 묶은 단위

## 평가 방식

- 평가 대상: 각 팀의 저장소와 최종 평가 면담
- 평가 시점: 최종 평가 당일(2026-12-09) **기본 브랜치**(main 등)의 내용
  - 다른 브랜치의 작업은 평가 전에 기본 브랜치에 병합해야 함
- 평가 범위: 강의 90(LLMOps와 LLM 애플리케이션 보안)까지 다룬 내용
- 저장소 공개: 저장소는 공개(public)를 원칙으로 함
  - API 키, 인증 토큰 등 비밀 값은 커밋하지 않음(환경 변수나 `.env`로 관리하고 `.env`는 `.gitignore`에 포함)
- 면담
  - 교수가 무작위로 다양한 케이스에 대한 실행을 요청할 수 있음(예: 요청을 실행해 운영 기록 `logs/trace.jsonl`에 남는지 확인)
  - 저장소의 항목(실패 케이스, 개선 회차, 공격 케이스)을 골라 그 근거를 물음

| 개선 회차 | 회차마다 가설 하나의 수정을 커밋하고 기존 러너로 측정 / 회차 번호는 R1부터 순서대로 붙임 / 수정 커밋 메시지의 제목과 `history.csv`의 `change`에 같은 문자열 `R<번호> | 대상: <케이스 id> | 가설: <한 문장>`을 기재(`change`는 러너의 `--change` 인수로 전달, `change` 열이 없으면 추가) / 채택한 회차는 수정 커밋을 유지 / 기각한 회차는 `git revert <수정 커밋>`으로 되돌리고 되돌림 커밋 메시지의 본문에 판정 근거 기재(제목에는 원래 커밋 제목이 자동으로 들어감) |
| 위협 목록 | `docs/ARCHITECTURE.md`에 위협 목록 절 추가: 위협 3개 이상, 위협마다 자산, 진입점, 공격자 목표, 대응, 연결된 공격 케이스 id |
| 공격 케이스 측정 | 공격 케이스 5건 이상을 기존 `evals/evalset.jsonl`에 공격 범주로 추가(케이스마다 공격 성공 판정, 기존 injection 케이스 포함 가능) / 기존 러너가 공격 성공률(공격 케이스 중 공격 성공 건수의 비율)을 집계해 `history.csv`의 `attack_success_rate` 열에 기록(공격 범주와 정상 범주를 같은 실행에서 측정) |

## `history.csv` 기록 방법

### 파일이 깨지지 않게 기록하기

- Excel에서 한글이 깨지거나 열이 밀리는 원인: BOM(Byte Order Mark, 파일 맨 앞에서 UTF-8임을 알리는 3바이트 표시) 없는 UTF-8 파일을 한국어 Windows의 Excel이 CP949로 읽음. 한글 바로 뒤의 쉼표가 글자 일부로 해석되어 두 열이 합쳐지기도 함
- 인코딩: BOM이 있는 UTF-8(`utf-8-sig`)로 저장. Python에서 읽을 때도 `encoding="utf-8-sig"`
- 수동으로 편집한다면 반드시 BOM이 있는 UTF-8로 저장(Windows 메모장은 '다른 이름으로 저장'의 인코딩에서 'UTF-8(BOM)' 선택)
- 쓰기 방식: 문자열을 직접 이어 붙이지 말고 표준 CSV 라이브러리(Python `csv.DictWriter`)로 한 줄씩 추가. 값에 쉼표나 따옴표가 있어도 라이브러리가 따옴표로 묶어 열이 어긋나지 않음
- 열 구분자는 쉼표(`,`). 값 안에서 항목을 나눌 때는 ` | `를 씀(쉼표를 피하면 사람이 읽기도 쉬움)
- 열을 추가할 때(`change`, `attack_success_rate`): 기존 열 순서는 그대로 두고 빠진 열만 뒤에 붙인 뒤, 기존 행에는 빈 값을 넣어 파일 전체를 `utf-8-sig`로 한 번 다시 저장
- 확인: 저장한 파일을 Excel로 열어 한글과 열 개수가 맞는지 확인

러너에서 한 줄을 추가하는 코드(열 목록은 팀의 지표에 맞게 바꿀 것):

```python
import csv
from pathlib import Path

FIELDS = ["run_id", "commit", "change", "evalset_version", "judge_version", "golden_tests",
          "constraint_satisfaction", "explanation_quality", "hallucinated_names", "attack_success_rate"]
path = Path("evals/results/history.csv")

def append_history(row: dict) -> None:
    new_file = not path.exists()
    with path.open("a", encoding="utf-8-sig", newline="") as f:  # BOM은 새 파일의 맨 앞에만 기록됨
        writer = csv.DictWriter(f, fieldnames=FIELDS, restval="")
        if new_file:
            writer.writeheader()
        writer.writerow(row)
```

기존 파일을 한 번 변환하는 코드(인코딩 변경과 열 추가를 함께 처리):

```python
rows = list(csv.DictReader(path.open(encoding="utf-8-sig", newline="")))
with path.open("w", encoding="utf-8-sig", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=FIELDS, restval="")
    writer.writeheader()
    writer.writerows(rows)
```

### 열 설명

- `run_id`: 실행 시각(`YYYY-MM-DDTHHMM`). 같은 실행의 결과 파일 `evals/results/<run_id>.json`과 이름이 같음
- `commit`: 측정한 코드의 커밋 해시(짧은 형식)
- `change`: 무엇을 하려고 한 실행인지. 러너의 `--change` 인수로 전달
  - 기준점 측정: `기준점 1/3`, `기준점 2/3`, `기준점 3/3`
  - 개선 회차: `R<번호> | 대상: <케이스 id> | 가설: <한 문장>`. 번호는 R1부터 순서대로 붙이고, 수정 커밋 메시지의 제목과 같은 문자열을 씀
- `evalset_version`: 평가 세트의 케이스 수와 파일 해시(`27 cases | 5d2a8f1`). 이 값이 같은 실행끼리만 비교
- `judge_version`: judge 프롬프트 버전. 이 값이 같은 실행끼리만 비교
- `golden_tests`: 골든 테스트 결과(`6/6 passed`). 러너의 `--golden` 인수로 전달
- 지표 열: `EVAL_DESIGN.md` 1절에서 정한 지표(팀마다 다름). 단골은 `constraint_satisfaction`(제약 충족률), `explanation_quality`(설명 품질 통과율), `hallucinated_names`(없는 식당 이름 건수)
- `attack_success_rate`: 공격 범주 케이스 중 공격이 성공한 비율(0~1, 낮을수록 좋음). 공격 범주와 정상 범주를 같은 실행에서 측정

수치, 요청 id, 커밋은 설명용 예시 값이다. 열 구성은 팀의 기존 파일을 따른다.

추적 기록 `logs/trace.jsonl`의 한 줄:

```json

```

추적 기록에서 추가한 실패 케이스와 공격 케이스(`evals/evalset.jsonl`):

```jsonl
{"id": "e22", "category": "constraint", "query": "비건인 친구랑 홍대에서 저녁", "expect": {"area": "홍대", "dietary": ["vegan"]}, "graders": ["code", "judge"], "note": "출처 q-0440. 동행자의 식이제약 누락"}

```

개선 회차의 수정 커밋과, 기각했을 때의 되돌림 커밋:

```
$ git commit -m "R2 | 대상: e3 | 가설: 검색 건수를 4에서 8로 늘리면 설명 품질이 오른다"
$ git revert b72d014    # 기각 시. 열리는 편집기에서 본문에 판정 근거를 추가
```

되돌림 커밋 메시지(제목은 git이 자동으로 만듦):

```
Revert "R2 | 대상: e3 | 가설: 검색 건수를 4에서 8로 늘리면 설명 품질이 오른다"

This reverts commit b72d014.

기각: 설명 품질 차이 0.071(기준점 0.786 → 0.857)이 변동 폭 0.071 이하, 지연 p50 2.1초 → 3.4초
```

## 기타

- 골든 테스트는 평가 시점에 통과해야 함
- AI로 초안을 만들어도 되지만 다음은 사람이 정함: 실패 케이스와 공격 케이스의 기대 결과와 성공 판정, 개선 회차의 채택과 기각
- 공격 대상은 우리 팀의 제품뿐이며 실제 개인정보를 쓰지 않음
