# 승부처 방식 설계안

| 항목 | 값 |
|---|---|
| 상태 | 제안. 분류·승부처 API·화면을 구현했다. SPEC·AC에는 아직 반영하지 않았다 |
| 작성일 | 2026-11-25 |
| 근거 | [MVP 사용 피드백 7건](#5-피드백과의-대응), 2026-11-25 실제 서비스 3인 방 사용 결과 |
| 구현 | [`src/travel/showdown.py`](../src/travel/showdown.py), [`src/travel/data/showdown_rules.json`](../src/travel/data/showdown_rules.json), [`src/travel/server/app.py`](../src/travel/server/app.py), [`web/src/pages/Showdown.tsx`](../web/src/pages/Showdown.tsx) |

이 문서는 팀 검토를 위한 설계안이다. [SPEC](SPEC.md)의 AC와 절대 규칙을 바꾸는 내용은 팀이 확정한 뒤 SPEC에 옮긴다.

## 1. 왜 바꾸는가

MVP 피드백에서 가장 많이 나온 문제는 협약서가 조율 결과가 아니라 응답 나열에 가깝다는 것이었다(4건). 2026-11-25에 실제 서비스에서 3인 방을 만들어 확인한 결과도 같았다.

- 6문항 중 4개가 조건부 대안으로 끝났고, 제안 조건은 모두 "확인해요", "정해요"로 끝났다.
- 응답자 중 한 명이 중간 선택지("두 곳을 고르고 남는 시간을 자유롭게")를 골랐는데도 조항은 동선을 셋으로 나눴다.
- 조건부 대안 4개 중 3개가 메모를 쓰지 않은 한 사람에게 변경을 요청했다. 두 번 생성해도 같았다.

원인은 프롬프트 문구가 아니라 조항의 정의다. 현재 조항은 "누구의 바람을 어떻게 조율할지"를 설명하는 문장이고, 모든 사람의 원래 조건을 보존해야 하며(AC6), 금액·시각을 확정할 수 없다(AC7). 이 조건에서는 결정이 담긴 짧은 규칙이 나올 수 없다.

## 2. 동작

### 흐름

2026-11-25 팀 결정: 승부처는 협약서를 보기 전 단계다.

1. 응답: 지금과 같다.
2. 분류(코드): 문항마다 통함, 중간 안, 승부처, 기본 절충안, 열림 중 하나로 가른다.
3. 승부처 확인하기: 응답이 마감되면 "협약서 보기" 대신 "승부처 확인하기"가 나온다. 누르면 갈린 문항 수와 진행 방법을 안내한다.
4. 승부 방법 선택: 각자 기기에서 절충안, 승부, 토론 중 하나를 고르고, 갈리면 가위바위보나 제비뽑기를 한다.
5. 전체 협약서 보기: 승부처를 모두 정하면 열린다. AI 추천 협약서를 위에, 한 줄 약속 목록(통한 약속과 승부처 결과)을 그 아래에 둔다. 이 배치는 임시이며 확정되면 다시 고친다.

승부처가 없는 방은 3·4단계를 건너뛰고 바로 협약서를 본다. 승부처가 남은 채 협약서 주소를 직접 열면 승부처로 안내한다.

### 분류 규칙

"어느 쪽이든 괜찮아요", "다른 의견이 있어요", "정보가 더 필요해요"는 표로 세지 않는다. 남은 표를 위에서부터 판정한다.

| 순서 | 조건 | 결과(`outcome`) | 규칙 문장 |
|---|---|---|---|
| 1 | 표가 없다 | `open` | 없음 |
| 2 | 표가 모두 같은 선택지다 | `agreed` | 그 선택지의 규칙 |
| 3 | 갈렸고 누군가 중간 선택지를 골랐다 | `middle` | 중간 선택지의 규칙 |
| 4 | 갈렸고 중간 선택지를 고른 사람이 없다 | 승부처 후보 | 아래 상한 적용 |

- 따로 행동하는 선택지는 전원이 골랐을 때만 2번으로 통한다. 한 명이라도 다른 선택지를 골랐으면 한쪽 입장으로 센다.
- 승부처 상한은 문항 수의 20%를 반올림한 값이다(6·7문항 1개, 8문항 2개).
- 후보가 상한보다 많으면 가장 팽팽한 문항부터 승부처(`showdown`)로 올린다. 1위 표의 비율이 낮을수록, 표가 많을수록, 문항 순서가 앞설수록 먼저다.
- 나머지 후보는 기본 절충안(`fallback`)으로, 그 문항의 첫 번째 절충 후보를 적용한다.
- 같은 응답이면 결과가 항상 같다. 모델을 호출하지 않는다.

### 승부처 카드

- 무엇이 갈렸는지 이름 없이 보여 준다(예: 생선 요리 vs 면 요리). 누가 어느 쪽인지와 인원수는 보여 주지 않는다.
- 각자 기기에서 넷 중 하나를 고른다: 절충 후보 1, 절충 후보 2, 승부하기, 토론해서 정할게요.
- 집계(제안): 한 명이라도 "토론해서 정할게요"를 고르면 미정으로 두고 일행이 직접 정한다. 전원이 같은 절충 후보를 고르면 확정한다. 그 밖에는 승부로 간다.
- 승부: 2명이면 각자 기기에서 가위바위보를 내고, 이긴 사람의 선택을 채택한다. 3명 이상이면 서버가 한 사람을 뽑아 그 사람의 선택을 채택한다(제비뽑기). 결과는 한 번 정하면 저장하고 다시 뽑지 않는다.

## 3. 규칙 문장

[규칙 데이터](../src/travel/data/showdown_rules.json)에 문항 50개의 선택지별 규칙과 절충 후보 2개를 미리 적어 둔다. 모델이 문장을 만들지 않는다.

| 필드 | 뜻 |
|---|---|
| `options.<option_id>.kind` | `side`(한쪽 입장), `middle`(중간), `split`(따로 행동) |
| `options.<option_id>.tag` | 승부처 카드에 보일 입장 이름 |
| `options.<option_id>.rule` | 그 선택지로 정해졌을 때의 한 줄 규칙 |
| `compromises[].type` | `alternate`(번갈아), `divide`(나누기), `split`(따로), `middle`(중간값) |
| `compromises[].rule` | 절충 후보의 한 줄 규칙. 첫 번째가 기본 절충안이다 |

문장 기준(테스트로 검사): 한 줄, 32자 이내, 이름 없음, "확인해요"·"정해요"·"조율"·"바람" 같은 표현 없음.

현재 문장은 AI가 쓴 초안이다. 선택지의 `kind` 분류와 문장은 팀이 검수해야 한다. 문장에 든 숫자는 문항 장면의 값이거나 기본값 제안이다.

## 4. 팀 결정과 남은 결정

2026-11-25에 정한 것.

1. 승부처는 각자 기기에서 진행한다.
2. 승부처는 문항의 20%까지다.
3. 규칙 문장과 절충 후보는 문항 pool 기준으로 미리 써 둔다.
4. "다른 의견이 있어요"를 골랐다고 그 문항을 승부처로 올리지 않는다.
5. 승부 여부는 일행이 고른다. 승부하지 않고 토론해서 정할 수 있다. 승부는 2명이면 가위바위보, 3명 이상이면 제비뽑기다.

아직 정하지 않은 것.

- SPEC 비포함 항목 "전원 수락 단계"와 AC6·AC7·AC8·AC9를 어떻게 고칠지. 현재 AC와 충돌하는 지점: 한 줄 규칙은 응답자별 원래 조건을 문장에 보존하지 않고(AC6), 장면의 숫자를 규칙에 쓴다(AC7).
- 메모의 지위. 현재 분류는 선택지만 본다. 메모가 선택을 뒤집은 경우(AC6)를 모델로 읽어 표에 반영할지 정해야 한다.
- 기존 추천 프롬프트·스키마·골든 케이스 30개·evals를 유지할지, 승부처 방식으로 바꿀지.
- 집계 규칙, 반올림 방식, 제비뽑기 방식은 위 2절의 제안값이다.
- 가위바위보가 비겼을 때의 처리(다시 내기 횟수).
- 3명 이상에서 이름·인원수 비공개를 유지할지.

## 5. 피드백과의 대응

| 피드백 | 이 설계에서 |
|---|---|
| 응답 나열, "함께 정해요"로 끝남 | 모든 문항이 한 줄 규칙이나 승부처로 끝난다 |
| 문항 안의 절충 선택지를 쓰지 않음 | 분류 규칙 3번 |
| 양보하는 사람이 결과마다 바뀜 | 분류가 코드라 같은 응답이면 같다. 양보는 일행이 승부처에서 정한다 |
| 이름과 메모가 드러남 | 규칙 문장에 이름이 없다 |
| 협약서가 길다 | 조항이 한 줄이다 |
| 방장만 다 한다 | 승부처는 각자 기기에서 참여한다 |

## 6. 서버와 화면

상태는 `rooms.showdown`(jsonb) 한 칸에 둔다. 응답이 고정된 뒤(`frozen_input`)부터 쓸 수 있고, AI 추천 생성과는 독립이다.

| 요청 | 누가 | 내용 |
|---|---|---|
| `GET /api/rooms/{code}/showdown` | 누구나. `X-Session-Id`가 제출한 세션이면 본인 선택이 함께 온다 | 한 줄 규칙 목록과 승부처 상태. 규칙 데이터에 없는 문항이 있으면 `{"available": false}` |
| `POST .../showdown/{scenario_id}/pick` | 제출한 세션(`session_id`) | `choice`: `c0`·`c1`(절충 후보), `duel`(승부), `talk`(토론). 전원이 고르기 전에는 바꿀 수 있다 |
| `POST .../showdown/{scenario_id}/move` | 승부에 참여한 두 사람 | `move`: `rock`·`paper`·`scissors`. 비기면 다음 판으로 넘어간다 |
| `POST .../showdown/{scenario_id}/close` | 방장 | 지금까지 모인 선택으로 마감한다. 한 명 이상 골라야 한다 |

- 응답에는 누가 무엇을 골랐는지, 입장별 인원수, 참여자 ID가 없다. 승패(`won`)와 낸 패는 승부에 참여한 본인에게만 간다.
- 화면은 `/r/{code}/showdown`이다. 진행 상황 화면과 "협약서 보기" 자리의 버튼이 승부처가 남은 동안 이곳으로 보낸다. 3~5초마다 다시 조회해 다른 기기의 선택을 반영한다.
- 모의 모드(`npm run dev:mock`)는 승부처를 지원하지 않는다. 로컬 확인은 `LLM_MODE=replay` 서버로 한다.
- 배포할 때 DB에 `rooms.showdown` 칸이 필요하다. `init_schema`가 `ADD COLUMN IF NOT EXISTS`로 더한다.
