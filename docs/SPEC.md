# 제품 스펙 v2: 여행 동행 협약서

## 1. 문제

친구·연인·가족 등 동행과 자유여행을 하는 사람이 일정·활동을 조율할 때 바람과 한계를 충분히 말하거나 반영하기 어려워하며, 일부는 조율 뒤에도 아쉬움이나 준비 부담을 겪는다. 조율 결과와 남은 부담의 근거는 [문제 정의서](PROBLEM.md)에 정리한다.

## 2. 타깃 사용자

친구·연인·가족 등 동행과 자유여행을 앞두고 일정·활동을 함께 정하는 사람. 동행 관계는 제한하지 않는다. 혼자 여행하는 사람, 단체 일정 운영자, 여행 중 실시간 예약·동선 조정을 원하는 사람은 현재 대상에서 제외한다.

모바일 웹으로 제공한다. [9/23 회의](meetings/2026-09-23.md#기획)의 사전 체험과 [9/30 회의](meetings/2026-09-30.md#기획)의 방장 편집 방향을 반영한다. 참여·개인화·운영 정책의 현재 기준은 이 문서의 4~6절이며, 구현 완료를 뜻하지 않는다.

모델·운영 정책과 유머 표시의 후속 결정은 [9/30 회의록의 추가 기록](meetings/2026-09-30.md#회의-이후-추가-결정-2026-10-01)을 따른다.

## 3. 핵심 기능

여행 정보에 맞는 같은 가상 상황 6~8개에 각자 답하면, 제출된 응답의 요구와 한계를 반영한 추천 협약서를 만들고 방장이 결과 선택·편집 후 이름·별명이 표시된 이미지로 저장·공유한다.

출력은 `PactRecommendation`이다. 전원 동의 단계는 두지 않으며 생성·편집·저장을 실제 결정인 `Decision`이나 동행 전원의 수락으로 기록하지 않는다. 사용자에게는 ‘여행 동행 협약서’, 발급 표시는 ‘추천안 발급’으로 보여준다.

화면 구상은 종이 협약서가 펼쳐지고 붉은 도장이 찍히는 연출이다. 도장에는 ‘추천안 발급’을 표시한다.

## 4. 범위

### 포함

| 식별자 | 기능 | 기준 |
|---|---|---|
| F1 | 방장이 여행 정보와 일행 프로필을 한 번에 입력하고 링크로 초대한다. | 이름·별명은 필수, 성별·나이대·MBTI는 선택이다. 로그인 없이 이름을 선택한다. |
| F2 | 확정한 pool v2에서 AI가 문항 6~8개를 선정·각색한다. | 같은 상황·선택지를 제공하며 본인은 ‘당신’, 다른 동행은 등록한 이름·별명으로 표시한다. |
| F3 | 각자 객관식과 선택 메모로 답한다. | 제출 전까지 수정할 수 있다. 같은 이름의 별도 제출도 각각 집계하고 타인의 원문은 공개하지 않는다. |
| F4 | 설정 인원만큼 제출되거나 방장이 조기 생성을 요청하면 응답을 마감하고 추천을 생성한다. | 채택된 답변만 사용한다. 재질문 없이 가능한 일부 조항을 반환하고 조건부 대안·제외 사유를 구분한다. |
| F5 | 방장이 같은 답변으로 정상 결과를 한 번 재생성하고 결과 선택·문구 편집 후 이미지를 저장한다. | 최초·재생성 결과 중 하나를 고른다. AI 원본을 보존하고 편집본에 ‘방장 수정’을 표시한다. |
| F6 | 응답 완료·추천 생성 시 권한을 허용한 사용자에게 푸시를 보낸다. | 방장에게 완료를, 참여자에게 생성을 알린다. 자동 생성 성공 시 방장의 두 알림은 한 번으로 묶는다. |
| F7 | 방·프로필·답변·추천 결과를 방 생성 후 30일간 보관한다. | 만료 후 서버 자료를 삭제하고 초대 링크 조회를 차단한다. 사용자가 저장한 이미지는 남는다. |

추천 품질 스파이크의 판단에 따라 F4는 시제품 구현 범위에 유지하되 실제 서비스의 자동 발급 채택은 보류한다. 채택 조건은 6절 AC6~AC9의 공통 평가 기준이다. 문항 9건·추천 12건의 기술 재점검과 문항 v4 표현 점검 1건은 해당 조건에서의 진단 근거다. 단일 상황의 요구 보존·조건 분리는 [별도 12건 평가](spikes/grounded_pact.md#핵심-조율-품질의-별도-평가)로 판정한다. F4 전체 채택에는 [최신 버전의 다문항 연결·전체 정보 부족·미해결 분기 검증](spikes/grounded_pact.md#기술-점검-현황)도 필요하다. 방·권한·응답 수집·알림·이미지 저장은 제품 구현 검증 범위이며, 이번 실험은 모델 출력과 두 생성 단계의 연결을 다뤘다.

### 비포함

- 여행 중 실시간 조율, 실시간 최적 동선, 지도·영업·예약 정보 조회와 예약·결제·정산 실행.
- 성격·궁합 점수, 고정 성향 판정, 컨디션 수치화, 누가 옳은지 판정하는 기능.
- 로그인·실명 본인 확인, 이름에 따른 중복 참여 차단, 제출 후 답변 수정, 생성 시작 후 추가 제출.
- 전원 수락 단계, 법적 효력·전자서명, 다국어, 미응답자 재촉 알림.

도메인의 범위 밖은 [온톨로지](ontology.yaml)와 연결한다. 로그인·알림 등의 운영 범위는 이 스펙에서 정한다.

### 처리 정책

| 항목 | 정책 |
|---|---|
| 프로필·개인화 | 방장이 서로 구분할 이름·별명을 등록한다. 선택 정보는 문항 개인화에만 사용하고 프로필 자체는 공개하지 않는다. MBTI 등으로 답하지 않은 선호·한계를 채우지 않는다. 이름 선택·문항·결과에는 등록한 이름·별명을 사용한다. |
| 입장·중복 이름 | 초대 링크에서 자신의 이름을 선택한다. 그 이름으로 제출된 답변이 있으면 선택란 아래에 빨간 안내 문구를 표시하되 진행을 허용한다. 이름은 표시·프로필 연결용이며 본인 확인이나 중복 차단 기준이 아니다. |
| 제출·자동 생성 | 한 제출 건은 전체 문항의 답변 묶음이다. 같은 이름이라도 별도로 제출한 묶음에는 서로 다른 `participant_id`를 부여한다. 유효한 제출 건수가 `party_size`에 도달하면 ‘전원 완료’로 처리하고 한 번 자동 생성한다. 이는 실제로 서로 다른 사람이 모두 답했다는 확인이 아니다. |
| 조기 생성·마감 | 기본은 설정 인원만큼 제출될 때까지 대기한다. 방장은 그 전에 모인 완전한 제출 건으로 생성할 수 있다. 0건이면 생성을 시작하지 않는다. 생성 시작과 함께 입력을 고정하고 마감하며 늦은 제출은 거부한다. 결과에는 반영한 응답 수와 등록 명단 중 반영되지 않은 이름의 의견이 포함되지 않았음을 표시한다. |
| 재생성·실패 | 방장은 같은 고정 입력으로 정상 결과를 한 번 재생성할 수 있다. 최초·재생성 결과를 모두 보존하고 하나를 선택한다. 형식 오류·호출 실패의 재시도는 정상 결과 재생성 횟수에 포함하지 않는다. 실패로 새 응답을 받거나 입력을 바꾸지 않는다. |
| 방장 편집 | 선택한 결과의 조항 문구만 수정한다. 조항 추가·삭제, 근거·적용 대상 변경은 지원하지 않는다. 원본을 보존하고 화면·이미지에 ‘방장 수정’을 표시한다. 원본의 검증 결과를 편집본의 품질 보증으로 사용하지 않는다. |
| 응답·결과 공개 | 제출 전에 “선택과 메모 원문은 다른 사람에게 공개되지 않아요. 다만 답변에 담긴 바람과 한계는 선택한 이름과 함께 추천 결과에 반영될 수 있어요.”를 안내한다. 개인 선택·메모 원문과 성별·나이대·MBTI는 다른 참여자와 공유 이미지에 공개하지 않는다. 조율에 필요한 희망·한계는 추천 문장에 반영하며 적용 대상은 등록한 이름·별명으로 표시한다. 같은 이름의 서로 다른 제출은 ‘이름(응답 1)’, ‘이름(응답 2)’처럼 구분한다. |
| 문항 pool | [서비스용 pool v2의 50개 문항](../src/travel/data/scenario_pool.json)을 사용한다. [문항별 근거표](research/scenario_pool.md)에서 인터뷰·국내외 웹 경험담·공식 안내의 확인 내용과 가상 설정을 구분한다. 웹 자료는 인터뷰 근거와 별도로 관리한다. 주제별 필수 문항·고정 비중은 없다. 장소·활동만 다르고 판단 내용이 같으면 하나만 뽑고, 같은 주제라도 조건·고민이 다르면 함께 고를 수 있다. |
| 알림 | 허용된 푸시 구독으로만 보낸다. 자동 생성 성공 시 방장에게는 ‘협약서가 준비됐어요’ 한 번으로 완료·생성을 알린다. 자동 생성 실패 시에는 완료와 실패 상태를 알리고, 이후 성공 시 생성 알림을 보낸다. 푸시를 거부해도 화면에서 진행 상태·결과를 확인할 수 있다. |
| 만료 | 방 생성 시점부터 30일이며 재생성·편집으로 연장하지 않는다. 만료 후 원본·수정본·답변·프로필과 방에 연결된 접근·푸시 정보를 삭제하고 조회·제출·재생성·푸시를 중단한다. 저장 이미지에는 서버 삭제가 적용되지 않는다. |
| 모델·검증 환경 | 모델은 GPT-6.1 Sol (`gpt-6.1-sol`, 이하 Sol)을 사용한다. 실험에는 모델 ID·설정·입력·최초 출력을 기록하며 서비스 API 연결·스키마 수용·비용·지연은 구현 검증에서 확인한다. 아이폰 Safari와 안드로이드 Chrome을 실제 기기로 확인한다. |

## 5. 인터페이스

이 절은 프레임워크와 HTTP 경로에 독립적인 논리 입출력 계약이다. 이름 선택은 인증이 아니므로 방장 권한은 방 생성 시 발급하는 별도 권한으로 서버에서 확인한다.

온톨로지의 `classes`는 인터뷰 개념, `output_contracts`는 제품 출력 모델이다. `TravelSituation`과 `Activity`를 가상 문항·선택지로 각색하고, 응답에서 드러난 `ParticipantPosition`을 바탕으로 `AdjustmentOption`에 해당하는 추천 조항을 만든다. 제품용 프로필·제출 식별자를 인터뷰에서 발견한 클래스로 세지 않는다.

| 작업 | 입력 | 출력·동작 |
|---|---|---|
| 방 생성 | `trip: {destination, duration_days, party_size, relationship}`, `participant_profiles: [{profile_id, display_name, gender?, age_band?, mbti?}]` | 방·초대 링크·방장 권한, 생성·만료 시각. 프로필 수는 설정 인원과 같다. |
| 입장·이름 선택 | 초대 링크, `profile_id` | 이름 선택과 기존 제출 여부 안내. 새 응답 작성 세션. 이름 중복을 이유로 차단하지 않는다. |
| 문항 선정·각색 | `{trip, participant_profiles, requested_count, scenario_pool, request}` | `ScenarioSet`: `{status, scenarios, clarification_questions?, message?}` |
| 답변 제출 | 작성 세션, `profile_id`, 전체 문항의 `{scenario_id, option_id, memo}` | 별도 `participant_id`와 문항별 `response_id`. 제출 후 수정 불가. |
| 생성·조기 생성 | 제출 수 도달 이벤트 또는 방장 요청 | 응답을 마감하고 채택한 제출·문항을 고정한다. 제외 안내·반영 건수는 서버가 계산한다. |
| 추천 협약서 생성 | `{participant_ids, scenarios, responses, request}` | `PactRecommendation`: `{status, positions, clauses, conditional_alternatives?, unresolved_conditions?, message?}` |
| 재생성·결과 선택 | 방장 권한, 고정 입력·결과 식별자 | 같은 입력의 두 번째 정상 결과 또는 선택한 결과. 세 번째 정상 결과 생성은 거부한다. |
| 방장 편집·이미지 저장 | 방장 권한, 선택한 결과, 조항 문구 수정 | 원본과 구분한 수정본·이미지. 이름·별명, 추천·조건부 대안·제외 안내·수정 표시를 유지한다. |
| 푸시 등록·발송 | 알림 권한·구독, 방의 완료·생성 이벤트 | 허용된 구독에만 발송하고 같은 이벤트의 중복 알림을 막는다. |
| 만료 처리 | 방 생성 시각 + 30일 | 서버 자료 삭제 및 링크 접근·작업 거부. |

### 필드 연결과 검증 경계

- 문항 프롬프트 v6는 [문항 스키마 v2](../src/travel/schemas/scenario_set.schema.json), 추천 프롬프트 v10은 [추천 스키마 v4](../src/travel/schemas/pact_recommendation.schema.json)를 사용한다. 추천은 같은 호출에서 `ParticipantPosition`도 추출한다. 추가 LLM 호출 없이 원본·입장·조항을 대조한다.
- `profile_id`는 등록 프로필, `display_name`은 이름·별명이다. 문항의 `{{profile:profile_id}}` 표기는 코드가 조회해 본인에게 ‘당신’, 다른 사람에게 등록한 이름으로 바꾼다. 모두 같은 문항·선택지 ID와 의미를 유지하며 선택 프로필 정보를 그대로 노출하지 않는다. 표시 이름·‘당신’의 받침에 맞게 이/가·은/는·과/와를 처리한다.
- [pool 데이터](../src/travel/data/scenario_pool.json)는 `pool_version`과 `scenario_pool`을 저장한다. 모델에는 문항 배열만 전달하고 출처·작성 근거는 입력에서 제외한다. 숙박·다음 날·2박 등 장면의 적용 조건은 여행 기간과 대조해 선정한다.
- pool의 `decision_key`는 같은 판단을 묻는 문항의 식별자다. 각 문항에 부여한 키를 유지하고 같은 키의 문항을 함께 선정하지 않는다. 주제 자체는 중복을 금지하는 기준이 아니다.
- 코드가 문항을 확정한 뒤 `scenario_id=template_id`로 연결하고 `core_constraints`를 pool에서 조회한다. 질문 모델의 미검증 출력을 추천 모델에 바로 전달하지 않는다.
- 방 생성의 `party_size`는 2 이상이며 자동 생성할 제출 수다. 문항 모델 계약의 `party_size>=1`과 제품 대상은 구분한다. 조기 생성에는 한 건 이상의 완전한 제출이 필요하다.
- `participant_id`는 채택한 제출 건의 식별자다. 같은 이름·프로필의 별도 제출도 다른 ID로 유지한다. 동일 제출 요청의 전송 재시도는 같은 건으로 처리한다. 이름 선택만으로 기존 제출의 소유권이나 수정 권한을 부여하지 않는다.
- 추천의 `participant_ids`에는 고정한 완전 제출 건만 넣는다. 미응답 등록 프로필은 모델 입력에서 제외하며 서버가 결과에 제외 안내를 붙인다. 자동 생성도 중복 이름으로 인원이 채워졌다면 반영되지 않은 등록 프로필을 안내한다. 마감과 마지막 제출·조기 생성이 겹쳐도 입력 고정과 최초 생성을 한 번만 수행한다.
- 각 제출·상황 쌍에는 정확히 한 `response_id`가 있어야 한다. `source_response_ids`는 같은 상황의 실제 응답을 참조한다. 이름·성별·나이대·MBTI는 추천 입력에서 제외하고 표시 이름은 서버가 ID로 조회한다. 추천용 장면에서도 인물 표시는 안정된 식별자로 유지한다.
- 추천 공유 문장에서 사람은 `{{participant:participant_id}}`로 표시하고, 코드는 채택 제출의 이름·별명으로 치환한다. 은/는·이/가·을/를·과/와·으로/로는 토큰 뒤의 조사 쌍을 읽어 이름의 받침으로 선택한다(ㄹ 받침은 로). 같은 이름의 제출에는 `이름(응답 1)`처럼 번호를 붙이되 조사는 이름을 기준으로 선택한다. 받침을 판별하기 어려운 영문·숫자 별명은 뒤에 ‘님’을 붙여 처리한다. 문항의 profile 토큰과 제출 건의 participant 토큰은 별도 명단으로 조회한다. 알 수 없는 ID·미해결 토큰은 표시 오류로 처리하며 화면과 저장 이미지는 같은 렌더링 함수를 사용한다. 렌더링 결과는 텍스트로 출력하고 이름에 포함된 토큰을 다시 해석하지 않는다.
- `positions[].position`은 `ParticipantPosition`의 네 속성과 일치한다. `condition`은 피로·컨디션, `desired_action`은 선택·수정 메모의 희망 행동과 제한, `reason`은 명시 이유, `expressed_content`는 실제 전달했다고 명시한 관련 발언이다. 미확정 행동은 null, 근거 없는 선택 속성은 생략한다. 후처리는 응답별 누락·중복과 인용의 원문 일치를 검사한다. 공유 결과에서는 `positions` 전체를 제외한다. 같은 모델의 추출값끼리 일치해도 의미가 맞았다고 판정하지 않는다.
- `memo`는 추가 설명이며 동행에게 실제로 전달한 말인 `expressed_content`로 자동 변환하지 않는다. `proposed_conditions`는 새 약속, `required_changes`는 원래 조건과 제안 변경이다. 어느 것도 기존 합의·수락으로 표시하지 않는다.
- `required_changes.original_condition`은 서버가 원문과 대조하는 검증용 필드다. 공유 응답을 만들 때 이 필드·`positions`와 개인 응답 원문을 제외하고, 화면·이미지에는 `action`과 `proposed_change` 등 조율에 필요한 추천 문장만 표시한다. 표시 문장에도 메모를 그대로 인용하지 않으며, 이 기준은 방장 수정본에도 적용한다.

|---|---|---|

| `PactRecommendation` | `conditional_only` | `clauses=null`. 조건부 대안·미해결 조건·이유를 표시한다. |

| `PactRecommendation` | `unresolved` | 정보는 충분하지만 검토한 방식에서 안을 찾지 못했다. 조건부 대안도 없으며 막힌 조건을 설명한다. |
| `PactRecommendation` | `unsupported`, `invalid_input` | `clauses=null`, 지원 범위 또는 입력 오류를 안내한다. |

상태에 필요한 배열·문자열은 비어 있으면 안 된다. 입력 오류·지원 밖·채택된 제출 내 누락 검사 후 일반 조항이 있으면 `proposed`, 조건부 대안만 있으면 `conditional_only`, 둘 다 없고 정보가 부족하면 `needs_information`, 충분해도 안을 찾지 못하면 `unresolved`이다. 상세 후처리는 두 프롬프트 B절을 따른다.

JSON·스키마·상태 조합 오류는 이유를 붙여 최대 1회 재요청하고 다시 실패한 결과는 사용하지 않는다. 호출 실패는 실행 오류로 알리며 정상 결과 재생성 횟수에 포함하지 않는다. 실패 상태에서 재시도를 요청해도 같은 고정 입력을 사용한다. `unresolved`에서만 바이럴 문구 “너네 조합 꽝이니 여행 가지 마세요!”를 표시할 수 있다. 바로 옆에 “이번 응답 조건에서는 추천안을 찾지 못했습니다.”와 막힌 조건을 함께 표시한다. AC7에 따라 결과의 판단 대상은 이번 응답 조건이며, 사람의 성격·궁합 점수나 여행 실패 판정으로 저장·표시하지 않는다. 정보 부족·제출 누락·호출 오류에는 이 문구를 사용하지 않는다.

## 6. 수용 기준

EARS 문형으로 조건·서비스·동작을 명시한다. 케이스 ID는 구현 단계 골든 테스트의 식별자이다. 아래 표는 제품의 완료 기준이며 이번 모델 출력 검사 범위와 구분한다.

| AC | 요구사항 | 케이스·판정 방법 |
|---|---|---|
| AC1 [이벤트 기반] | 유효한 문항 요청이 오면, 서비스는 요청한 6~8개를 반환하고 문항·선택지 ID와 핵심 제약·선택 의미를 보존하며, 인원을 쓰면 본인을 포함한 총인원으로 표시한다. | `scenario_contract`: 기간·인원에 맞지 않는 문항을 제외한 뒤 선정 수와 `decision_key` 중복을 대조한다. 핵심 조건을 바꿔 부적합 문항을 끼워 넣으면 실패이다. 주제 고정 비중은 없으며 같은 주제·다른 고민은 함께 선정할 수 있다. |
| AC2 [예외 대응] | 필수 여행 정보·프로필 또는 여행 조건에 맞는 서로 다른 판단의 pool이 부족하면, 서비스는 `needs_information`으로 필요한 정보를 요청한다. 범위 위반은 `invalid_input`, 지원 밖 요청은 `unsupported`로 반환한다. | `scenario_input`: 기본 다섯 유형과 프로필 누락·수 불일치·중복 ID·선택 정보 생략을 검사한다. |
| AC3 [상시 적용] | 서비스는 다른 참여자에게 개인 선택·메모 원문, `positions`, `original_condition`, 선택 프로필 정보를 반환하지 않는다. | `response_privacy`: 제출 전에 원문 비공개와 바람·한계의 이름 포함 결과 반영 안내가 표시되는지 확인한다. 응답 조회와 공유 결과에서 원문·검증용 인용 필드가 제외되고, 공개 문장에도 메모가 그대로 인용되지 않는지 검사한다. 이름 재선택·다른 응답 ID 조회에도 같은 기준을 적용한다. 조율 조건의 의미와 적용 대상 이름은 표시할 수 있다. |
| AC4 [이벤트 기반] | 유효한 제출 수가 설정 인원에 도달하거나 방장이 조기 생성을 요청하면, 서비스는 입력을 한 번 고정하고 응답을 마감해 생성한다. | `response_closure`: 같은 이름의 별도 제출을 각각 집계한다. 조기 생성 0건은 거부하고 1건 이상은 허용한다. 동시 제출·조기 요청에서도 최초 생성은 한 번이며 이후 제출·수정은 거부한다. 제외 안내와 반영 건수를 검사한다. |
| AC5 [상시 적용] | 서비스는 같은 상황의 실제 응답만 근거로 사용하고 잘못된 ID·중복 응답 ID를 거부한다. | `evidence_integrity`: 같은 이름·서로 다른 제출 ID는 허용하고, 같은 제출·상황의 중복은 `invalid_input`으로 처리한다. 작성자·상황 연결을 대조한다. |
| AC6 [이벤트 기반] | 추천 요청이 오면, 서비스는 명시적 요구·한계와 선택을 수정한 메모를 보존하고 모호한 부분을 제외한 가능한 조항을 반환한다. | `memo_limits`: 같은 선택·다른 메모, 소수 한계, 타인 추측, 중복 이름의 다른 답변을 대조한다. 공동 차량의 일부 조항을 전체 이동 결정으로 표시하거나 제외된 사람에게 의무를 부과하면 실패이다. |
| AC7 [상시 적용] | 서비스는 새 약속을 `proposed_conditions`로 구분하고 가상 사실·추천을 실제 일정·전원 합의·성격·궁합 판정으로 표시하지 않는다. | `proposal_boundary`: 가상 숫자·예약·재합류 제안과 출력 표현을 대조한다. 등록 프로필을 답변 근거로 사용하지 않는지 검사한다. 고정 유머 문구 “너네 조합 꽝이니 여행 가지 마세요!”는 `unresolved` 화면에서만 예외로 허용한다. 바로 옆에 “이번 응답 조건에서는 추천안을 찾지 못했습니다.”와 실제 막힌 조건이 모두 표시돼야 통과한다. 다른 상태의 노출, 설명 누락, 궁합 점수·여행 실패 판정으로의 확장은 실패이다. |
| AC8 [복합 조건] | 원래 한계를 변경해야 가능한 대안을 제시하면, 서비스는 원문 조건·응답 근거를 서버에서 검증하고 사용자에게 변경 제안을 조건부 대안으로 표시한다. 그런 대안만 있으면 `conditional_only`로 반환한다. | `conditional_result`: R12처럼 메모를 인용한 `original_condition`은 서버에 유지하고 공유본에서 제외한다. 메모 우선 적용, `clauses=null`, 변경 제안과 수락의 구분을 검사한다. |
| AC9 [예외 대응] | 정보가 충분해도 검토한 방식에서 안을 찾지 못하면, 서비스는 `unresolved`와 막힌 조건을 반환한다. | `result_routing`: 부분 조항·조건부 대안·전체 정보 부족·전체 미해결·호출 오류를 나눠 상태 우선순위와 유머 표시를 검사한다. |
| AC10 [예외 대응] | 출력 형식 검사가 실패하면, 서비스는 이유를 붙여 최대 1회 재요청하고 다시 실패한 출력을 사용하지 않는다. | `output_validation`: JSON 절단·추가 키·잘못된 상태를 주입해 재요청 횟수, 결과 미사용, 정상 결과 재생성 횟수 미소비를 검사한다. |
| AC11 [예외 대응] | 프로필·여행 정보·pool·메모에 규칙 변경 지시가 있으면, 서비스는 이를 명령으로 실행하지 않고 출력 계약을 유지한다. | `untrusted_input`: 조작 지시 유무의 쌍에서 허위 동의·한계 무시·임의 필드·지시 유출이 없는지 검사한다. |
| AC12 [이벤트 기반] | 결과 수정 요청이 오면, 서비스는 별도 방장 권한과 조항 문구만 변경했는지 확인하고 원본과 구분된 수정본을 저장한다. | `host_edit`: 방장 이름 선택만 한 요청은 거부한다. 추가·삭제·근거·적용 대상 변경을 막고 원본·수정 표시를 확인한다. |
| AC13 [이벤트 기반] | 이미지 저장 요청이 오면, 서비스는 미리보기와 같은 이름·별명, 추천·조건부 대안·제외 안내·수정 표시를 포함한 이미지를 만든다. | `result_export`: AC3의 공개 기준을 원본·방장 수정본에 적용한다. `original_condition` 없이 변경 제안이 표시되는지, 같은 이름의 제출 구분과 화면·이미지가 일치하는지 검사한다. 참여자 토큰의 이름 치환과 조사 5쌍을 받침 유무·ㄹ 받침·중복 이름·영문/숫자 별명으로 검사하고, 없는 ID·남은 토큰은 표시를 막는다. |
| AC14 [상시 적용] | 서비스는 아이폰 Safari와 안드로이드 Chrome에서 응답·생성·편집·저장 흐름을 읽고 조작할 수 있게 하고 오류를 텍스트로 표시한다. | `mobile_access`: 두 실제 기기의 모델·OS·브라우저 버전을 기록하고 화면 잘림·포커스·레이블·이미지 저장·푸시 허용 및 거부 흐름을 확인한다. |
| AC15 [이벤트 기반] | 프로필을 이용해 문항을 표시하면, 서비스는 본인을 ‘당신’, 다른 동행을 등록한 이름·별명으로 바꾸고 모든 뷰의 상황·선택 의미를 유지한다. | `profile_rendering`: 선택 정보 유무와 이름 변경에 따른 뷰를 비교한다. 받침이 있는 이름·없는 이름·‘당신’에 이/가·은/는·과/와를 적용하고, 개발용 단순 치환에서 나온 ‘당신가·당신는·당신와’를 재현해 올바른 조사와 의미 보존을 확인한다. 성별·나이대·MBTI 노출과 선호·한계 추정, 없는 프로필 토큰을 거부한다. |
| AC16 [이벤트 기반] | 이미 제출된 이름을 선택하면, 서비스는 선택란 아래에 빨간 안내 문구를 표시하고 새 응답 작성을 허용한다. | `duplicate_name`: 같은 이름의 두 제출은 별도 ID로 저장한다. 전송 재시도는 동일 건으로 처리하고, 기존 제출 열람·수정은 허용하지 않는다. |
| AC17 [이벤트 기반] | 방장이 정상 결과 재생성을 요청하면, 서비스는 고정 입력으로 한 번 더 생성하고 두 결과 중 하나를 선택하게 한다. | `regeneration`: 입력 불변·두 결과 보존·선택·세 번째 정상 생성 거부를 검사한다. 실패 재시도는 재생성 횟수를 소비하지 않는다. |
| AC18 [이벤트 기반] | 응답 완료·협약서 생성 이벤트가 발생하면, 서비스는 권한을 허용한 해당 구독에 푸시를 보낸다. | `push_events`: 거부자에게 미발송, 방장 완료·참여자 생성 통지, 자동 생성 성공 시 방장 알림 한 번, 이벤트 재처리 시 중복 방지, 실패 후 성공 알림을 검사한다. |
| AC19 [상태 기반] | 방 생성 후 30일이 지나면, 서비스는 방 관련 서버 자료를 삭제하고 초대 링크 조회·제출·재생성·푸시를 거부한다. | `retention`: 만료 직전·정각·이후와 편집·재생성 후를 검사한다. 서버 자료는 삭제되고 기기에 저장한 이미지는 유지되는지 확인한다. |

AC6~AC9의 자동 발급 채택 조건은 [스파이크](spikes/grounded_pact.md)에서 사전에 정한 평가 세트의 80% 이상 통과와 허위 동의·명시적 한계 위반·원문 왜곡 0건이다. 새 품질 평가는 요청 12건으로 설계한다. 입력·기준 확정 작업 시작부터 준비·생성·검사·사람 판정·합의를 합쳐 최대 90분 동안 수행하고 실제 걸린 시간을 기록한다. 준비용 사례는 평가 12건에서 제외하고, 모델 출력 전에 입력·기준·설정을 고정한다. 기존 12건 회귀는 품질 합격률에 합산하지 않는다. 팀원 2명이 출력 생성 전에 입력별 기대 조건을 독립 작성·합의하고 생성 후에도 독립 판정한다. 구조 검사만 통과한 건은 최종 통과로 세지 않는다. 명확한 요구를 근거 없이 제외하거나 한계를 무시한 일부안을 만들면 건별 실패이다. 허용되는 조항·조건부 대안·제외 범위는 사람 기준과 대조한다. 과거 버전의 실험을 최신 추천 프롬프트의 채택 완료 근거로 대체하지 않는다. 전체 정보 부족·전체 미해결·인젝션·호출 오류와 신규 운영 정책의 AC는 별도로 검증한다.

2026-09-30 실험은 당시 pool v1을 사용해 문항 선정·각색과 협약서 생성으로 나눈다. 문항 실험은 AC1·AC2·AC11·AC15, 추천 실험은 AC5~AC9·AC11과 연결한다. 두 단계의 출력을 연결하는 점검도 수행한다. 결과는 입력·기대 조건·실제 출력·위반 근거·판정이 함께 보이는 표로 제시한다. 모델 출력 검사, 서비스 API 연동, 실제 사용 효과는 각각 수행한 검증 범위에 맞게 기록한다.

2026-09-30 기술 재점검의 반영: [문항 실험](spikes/scenario_adaptation.md)의 Q04에서 총인원 표현 모호성을 확인해 AC1과 문항 프롬프트 v4에 반영했다. [추천 실험](spikes/grounded_pact.md#5-결과)의 R10은 AC6의 일부 결과, R12는 AC8의 조건 변경, R04는 AC4·AC15의 채택 제출만 사용, R06은 AC11의 입력 지시 무시를 확인한 사례다. 자동 검사·AI 대조 결과를 사람 합의 평가의 최종 품질 점수로 대체하지 않는다.

### 서비스 API 검증

Sol 서비스 API가 두 출력 스키마를 수용하는지 확인하고 실제 비용과 지연을 측정한다. 방 500건의 전체 흐름을 기준으로 캐시·추론 토큰·실패 재시도·정상 결과 재생성을 포함해 예산을 확인한다. 모델 출력 검사 결과를 API 연동·비용·지연의 측정값으로 사용하지 않는다.

운영 계약은 위 AC의 케이스 ID에 맞춰 구현 설계와 골든 케이스에 반영한다. 방장 권한, 제출 건별 식별, 마감·동시 요청, 재생성·실패 재시도, 푸시 중복 방지와 만료 삭제를 포함한다. 실제 기기의 전체 흐름은 AC14, 문항의 이름·조사는 AC15, 추천 화면·이미지의 이름·조사는 AC13으로 검증한다.

### 제품 사용 검증

품질 기준을 충족한 추천을 실제 여행 그룹(친구·연인·가족)이 사용하는 모습을 관찰해 [PROBLEM의 해결 가설과 행동 지표](PROBLEM.md#해결-가설)를 확인한다. 관찰 전에 대상 그룹의 조건·수, 관찰 시간, 추천 활용률의 목표·기각 비율을 정하고 기록한다. 참가자는 실제 사람 단위로 확인하며 같은 이름의 여러 제출을 여러 사람으로 세지 않는다.

품질 기준을 충족한 결과를 읽고 관찰을 마친 그룹에서 사용할 조항 1개 이상 선택은 활용 성공, 0개는 활용 실패로 센다. 조항·적용 대상·이유를 기록하며 조건부 대안은 필요한 변경 조건까지 선택한 경우에만 센다. 논의 재시작은 보조 관찰이다. 응답 왜곡·한계 위반은 추천 품질 오류로, 여행 취소·결과 미열람 등은 관찰 중단으로 분리하고 대상 수·완료 수·중단 이유를 함께 기록한다. 결과 조회·이미지 저장을 전원 동의나 실제 여행의 갈등 감소로 해석하지 않는다. 이 관찰은 서비스 구현 후의 사용 검증이며 4강 모델 출력 실험의 성적에 포함하지 않는다.
