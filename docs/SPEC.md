# 도원결의 제품 스펙 v2

## 1. 문제

친구·연인·가족 등 동행과 자유여행을 하는 사람은 일정·활동을 함께 정할 때 서로 바람과 한계가 갈리는 일을 겪고, 일부는 바람을 말하지 못하거나 말해도 반영되지 않아 조율 뒤에도 아쉬움이나 준비 부담을 겪는다. 조율 결과와 남은 부담의 근거는 [문제 정의서](PROBLEM.md)에 정리한다.

## 2. 타깃 사용자

친구·연인·가족 등 동행과 자유여행을 앞두고 일정·활동을 함께 정하는 사람. 동행 관계는 제한하지 않는다. 혼자 여행하는 사람, 단체 일정 운영자, 여행 중 실시간 예약·동선 조정을 원하는 사람은 현재 대상에서 제외한다.

모바일 웹으로 제공한다. [9/23 회의](meetings/2026-09-23.md#기획)의 사전 체험과 [9/30 회의](meetings/2026-09-30.md#기획)의 방장 편집 방향을 반영한다. 참여·개인화·운영 정책의 현재 기준은 이 문서의 4~6절이며, 구현 완료를 뜻하지 않는다.

## 3. 핵심 기능

여행 정보에 맞는 같은 가상 상황 6~8개에 각자 답하면, 제출된 응답의 요구와 한계를 반영한 추천 협약서를 만들고 방장이 결과 선택·편집 후 이름·별명이 표시된 이미지로 저장·공유한다.

출력은 `PactRecommendation`이다. 전원 동의 단계는 두지 않으며 생성·편집·저장을 실제 결정인 `Decision`이나 동행 전원의 수락으로 기록하지 않는다. 서비스명은 ‘도원결의’이며 개발 팀은 ItBM이다. 결과물은 문서에서 ‘추천 협약서’로 부르고, 화면에는 ‘여행 동행 협약서’, 발급 표시는 ‘추천안 발급’으로 보여준다. 화면 연출은 [9/23 회의의 협약서 도출 방향](meetings/2026-09-23.md#협약서-도출-방향)을 참고한다.

## 4. 범위

### 포함

| 식별자 | 기능 | 기준 | AC |
|---|---|---|---|
| F1 | 방장이 첫 화면(랜딩)에서 방 만들기를 시작해 여행 정보와 일행 프로필을 단계별로 입력하면, 마지막에 한 번에 방을 만들고 링크로 초대한다. | 랜딩은 주 문구와 보조 문구, 예시 협약서, 3단계 안내를 보여 주고, 이 기기에 방장 권한이 남은 방을 이어갈 수 있게 한다. 예시에는 AC3의 비공개 항목을 넣지 않는다. 이름·별명은 필수, 성별·나이대·MBTI는 선택이며 선택 정보 단계는 건너뛸 수 있다. 선택 정보를 입력할 때 방장은 ‘동행에게 알렸어요’를 확인한다. 로그인 없이 이름을 선택한다. 방장은 생성이 끝난 방을 직접 삭제할 수 있다. | AC2, AC16, AC20 |
| F2 | 확정한 pool v3의 목록에서 AI가 `get_scenario_template` 도구로 원본을 확인해 문항 6~8개를 선정·각색한다. | 같은 상황·선택지를 제공하며 본인은 ‘당신’, 다른 동행은 등록한 이름·별명으로 표시한다. 도구 사용은 필수이며 pool 전체 입력 경로는 두지 않는다(2026-11-05 팀 결정). | AC1, AC2, AC11, AC15 |
| F3 | 각자 객관식과 선택 메모로 답한다. | 제출 전까지 수정할 수 있다. 같은 이름의 별도 제출도 각각 집계하고 타인의 원문은 공개하지 않는다. | AC3, AC5, AC16 |
| F4 | 설정 인원만큼 제출되거나 방장이 조기 생성을 요청하면 응답을 마감하고 추천을 생성한다. | 채택된 답변만 사용한다. 재질문 없이 모든 응답자의 확인 가능한 요구를 조율하고 일반 조항·조건부 대안·미해결 사유를 구분한다. | AC4~AC11 |
| F5 | 방장이 같은 답변으로 정상 결과를 한 번 재생성하고 결과 선택·문구 편집 후 이미지를 저장한다. | 최초·재생성 결과 중 하나를 고른다. 선택 전 결과는 ‘초안’으로 표시하고, 바로 아래에 ‘선택되지 않은 결과예요’를 작게 둔다. AI 원본을 보존하고 편집본에 ‘방장 수정’을 표시한다. 결과 화면 끝에서 결과 이미지와 서비스 링크를 공유하고 새 방 만들기로 갈 수 있다. 이미지를 미리 준비하고 다운로드와 파일 공유 버튼을 구분한다. 파일 공유에는 PNG만 전달하고, 저장이 안 되면 이미지 미리보기와 외부 브라우저 이용 방법을 안내한다. 버튼 근처에 이름이 보인다고 안내한다. 공유 문구에는 메모, 선택, 선택 프로필을 넣지 않는다. | AC12, AC13, AC17 |
| F6 | 응답 완료·추천 생성·방장의 결과 선택 시 권한을 허용한 사용자에게 푸시를 보낸다. | 방장에게 완료와 생성(또는 실패)을, 참여자에게 방장의 첫 결과 선택을 알린다. 초안 생성은 참여자에게 알리지 않는다. 자동 생성 성공 시 방장의 두 알림은 한 번으로 묶는다. | AC18 |
| F7 | 방·프로필·답변·추천 결과를 방 생성 후 30일간 보관한다. | 만료 후 서버 자료를 삭제하고 초대 링크 조회를 차단한다. 사용자가 저장한 이미지는 남는다. | AC19 |

AC14의 모바일 접근성은 모든 흐름에 적용한다.

1차 MVP의 구현 범위는 F1~F6이다. F7은 2026-11-17 이후 구현하며 2026-12-09 전 완료를 목표로 한다(2026-11-04·2026-11-05 팀 결정). 구현 상태는 [TODO](../TODO.md)에서 관리한다.

추천 품질 스파이크에서 단일 상황의 요구 보존·조건 분리는 [12건의 v11 사람 평가](spikes/grounded_pact.md#핵심-조율-품질의-별도-평가) 범위에서 채택했다. F4는 시제품 구현 범위에 유지하되 전체 자동 추천 채택은 보류한다. [v11 회귀 점검](spikes/grounded_pact.md#기술-점검-현황)에서 이름 조사 오류, AC7 미충족, 공유 조항의 개인 시간 조건 누락 가능성이 확인돼 보완 후 다시 판단한다. 채택 조건은 6절 AC6~AC9의 공통 평가 기준을 따른다. 방·권한·응답 수집·알림·이미지 저장은 제품 구현 검증 범위다.

### 비포함

- 여행 중 실시간 조율, 실시간 최적 동선, 지도·영업·예약 정보 조회와 예약·결제·정산 실행.
- 성격·궁합 점수, 고정 성향 판정, 컨디션 수치화, 누가 옳은지 판정하는 기능.
- 로그인·실명 본인 확인, 이름에 따른 중복 참여 차단, 제출 후 답변 수정, 생성 시작 후 추가 제출.
- 전원 수락 단계, 법적 효력·전자서명, 다국어, 미응답자 재촉 알림.

도메인의 범위 밖은 [온톨로지](ontology.yaml)와 연결한다. 로그인·알림 등의 운영 범위는 이 스펙에서 정한다.

### 처리 정책

| 항목 | 정책 |
|---|---|
| 프로필·개인화 | 방장이 서로 구분할 이름·별명을 등록한다. 선택 정보는 문항 개인화에만 사용하고 프로필 자체는 공개하지 않는다. MBTI 등으로 답하지 않은 선호·한계를 채우지 않는다. 이름 선택·문항·결과에는 등록한 이름·별명을 사용한다. 문항 모델을 호출하기 직전에 서버가 `display_name`을 ‘친구1’, ‘친구2’ 같은 자리표시자로 바꿔 보내고, 등록한 이름은 서버에만 둔다(2026-11-05 결정). 입력 규칙·스키마·문항 프롬프트·검증기는 바꾸지 않는다. |
| 입장·중복 이름 | 초대 링크에서 자신의 이름을 선택한다. 이름 선택 화면에는 방장이 이름·선택 정보를 등록했다는 사실, 사용 목적, 삭제 요청 방법을 쉬운 문구로 안내하고 [처리방침](PRIVACY.md)을 링크한다(2026-11-05 결정). 그 이름으로 제출된 답변이 있으면 선택란 아래에 빨간 안내 문구를 표시하되 진행을 허용한다. 이름은 표시·프로필 연결용이며 본인 확인이나 중복 차단 기준이 아니다. |
| 제출·자동 생성 | 한 제출 건은 전체 문항의 답변 묶음이다. 같은 이름이라도 별도로 제출한 묶음에는 서로 다른 `participant_id`를 부여한다. 유효한 제출 건수가 `party_size`에 도달하면 ‘전원 완료’로 처리하고 한 번 자동 생성한다. 이는 실제로 서로 다른 사람이 모두 답했다는 확인이 아니다. |
| 조기 생성·마감 | 기본은 설정 인원만큼 제출될 때까지 대기한다. 방장은 그 전에 모인 완전한 제출 건으로 생성할 수 있다. 0건이면 생성을 시작하지 않는다. 생성 시작과 함께 입력을 고정하고 마감하며 늦은 제출은 거부한다. 결과에는 반영한 응답 수와 등록 명단 중 반영되지 않은 이름의 의견이 포함되지 않았음을 표시한다. |
| 재생성·실패 | 방장은 같은 고정 입력으로 정상 결과를 한 번 재생성할 수 있다. 최초·재생성 결과를 모두 보존하고 하나를 선택한다. 선택 후 후보 탭은 접고 선택본을 표시하며, ‘다른 결과 보기’에서 다시 비교할 수 있다. 미선택 후보의 화면·이미지에는 초안 표시를 유지한다. 형식 오류·호출 실패의 재시도는 정상 결과 재생성 횟수에 포함하지 않는다. 실패로 새 응답을 받거나 입력을 바꾸지 않는다. |
| 방장 편집 | 선택한 결과의 조항 문구만 수정한다. 조항 추가·삭제, 근거·적용 대상 변경은 지원하지 않는다. 원본을 보존하고 화면·이미지에 ‘방장 수정’을 표시한다. 저장한 수정본은 바로 공개한다. 원본의 검증 결과를 편집본의 품질 보증으로 사용하지 않는다. |
| 응답·결과 공개 | 제출 전에 “선택과 메모 원문은 다른 사람에게 공개되지 않아요. 다만 답변에 담긴 바람과 한계는 선택한 이름과 함께 추천 결과에 반영될 수 있어요.”를 안내한다. 응답 화면에는 이와 별개의 문구로 건강 상태 등 조율에 필요하지 않은 개인 사정을 메모에 쓰지 않도록 안내한다(2026-11-05 결정). 개인 선택·메모 원문과 성별·나이대·MBTI는 다른 참여자와 공유 이미지에 공개하지 않는다. 여행 정보 중 목적지·기간·인원은 입장 화면, 협약서, 공유 이미지에 표시하고 동행 관계는 표시하지 않는다(2026-11-05 결정). 조율에 필요한 희망·한계는 추천 문장에 반영하며 적용 대상은 등록한 이름·별명으로 표시한다. 같은 이름의 서로 다른 제출은 ‘이름(응답 1)’, ‘이름(응답 2)’처럼 구분한다. 방장이 결과를 고르기 전에는 최초 정상 결과를 ‘초안’으로 공개하고, 고른 결과는 초안 표시 없이 공개한다. 재생성 결과는 방장이 고르기 전까지 방장에게만 보이며 기존 공개 결과는 유지한다. 참여자 결과 화면은 보이는 동안 초안을 3~5초, 선택본을 30초 간격으로 조회한다. 화면 복귀 시에는 즉시 조회하며, 숨겨진 화면이나 삭제된 방에서는 조회를 중단한다. 방장의 선택·수정은 원문 충실성 검증이나 동행 전원의 동의를 뜻하지 않는다(2026-11-05 팀 결정). |
| 문항 pool | [서비스용 pool v3의 50개 문항](../src/travel/data/scenario_pool.json)을 사용한다. [문항별 근거표](research/scenario_pool.md)에서 인터뷰·국내외 웹 경험담·공식 안내의 확인 내용과 가상 설정을 구분한다. 웹 자료는 인터뷰 근거와 별도로 관리한다. 주제별 필수 문항·고정 비중은 없다. 장소·활동만 다르고 판단 내용이 같으면 하나만 뽑고, 같은 주제라도 조건·고민이 다르면 함께 고를 수 있다. |
| 알림 | 허용된 푸시 구독으로만 보낸다. 자동 생성 성공 시 방장에게는 ‘협약서가 준비됐어요’ 한 번으로 완료·생성을 알린다. 자동 생성 실패 시에는 완료와 실패 상태를 알리고, 이후 성공 시 생성 알림을 보낸다. 참여자에게는 방장이 처음 결과를 골랐을 때 한 번 알리고, 초안 생성·재선택·수정 때는 보내지 않는다. 현재 기기의 해당 방 구독은 화면에서 해제할 수 있다. 같은 기기의 다른 방과 다른 기기는 유지하고, 재등록 시 과거 이벤트를 재발송하지 않는다. 해제된 구독의 발송 대기는 건너뛰지만 외부 전송을 시작한 알림은 회수하지 못한다. 발송 전 DB 점검이 실패하면 미발송 상태로 남기고 자동 재처리는 하지 않는다. 화면의 서비스 워커 활성화 대기는 5초로 제한하고 실패 시 재시도를 안내한다. 푸시를 거부해도 화면에서 진행 상태·결과를 확인할 수 있다. 아이폰은 홈 화면에 추가한 웹앱에서만 웹 푸시를 받을 수 있어, 아이폰 Safari 사용자는 푸시 대신 화면에서 확인한다. |
| 직접 삭제 | 방장만 방 전체를 삭제할 수 있다. 문항 준비 또는 협약서 생성 중에는 거부한다. 확인 후 방 관련 서버 자료를 함께 삭제하고 링크 접근을 차단한다. 성공한 기기에서는 해당 방의 저장 정보만 정리한다. 호출 장부는 방 연결을 끊고 기존 메타데이터와 비용을 2027-01-12 운영 정리까지 보존한다. 일일 비용 한도에 계속 포함하며, 사용자 삭제와 관리자 삭제에 같은 기준을 적용한다. 저장 이미지는 남는다. |
| 만료 | 방 생성 시점부터 30일이며 재생성·편집으로 연장하지 않는다. 만료 후 원본·수정본·답변·프로필과 방에 연결된 접근·푸시 정보를 삭제하고 조회·제출·재생성·푸시를 중단한다. 저장 이미지에는 서버 삭제가 적용되지 않는다. |
| 모델·검증 환경 | 모델은 GPT-6.1 Sol (`gpt-6.1-sol`, 이하 Sol)을 사용한다. 실험에는 모델 ID·설정·입력·최초 출력을 기록한다. 서비스 API 연결·스키마 수용·비용·지연은 구현 검증에서 확인했다. 아이폰 Safari와 안드로이드 Chrome을 실제 기기로 확인한다. |

## 5. 인터페이스

이 절은 프레임워크와 HTTP 경로에 독립적인 논리 입출력 계약이다. 이름 선택은 인증이 아니므로 방장 권한은 방 생성 시 발급하는 별도 권한으로 서버에서 확인한다.

온톨로지의 `classes`는 인터뷰 개념이고, 제품 출력 모델은 아래 [출력 모델](#출력-모델) 표와 JSON Schema가 정한다. `TravelSituation`과 `Activity`를 가상 문항·선택지로 각색하고, 응답에서 드러난 `ParticipantPosition`을 바탕으로 `AdjustmentOption`에 해당하는 추천 조항을 만든다. 제품용 프로필·제출 식별자를 인터뷰에서 발견한 클래스로 세지 않는다.

| 작업 | 입력 | 출력·동작 |
|---|---|---|
| 방 생성 | `trip: {destination, duration_days, party_size, relationship}`, `participant_profiles: [{profile_id, display_name, gender?, age_band?, mbti?}]` | 방·초대 링크·방장 권한, 생성·만료 시각. 프로필 수는 설정 인원과 같다. |
| 입장·이름 선택 | 초대 링크, `profile_id` | 이름 선택과 기존 제출 여부 안내. 새 응답 작성 세션. 이름 중복을 이유로 차단하지 않는다. |
| 문항 선정·각색 | `{trip, participant_profiles, requested_count, scenario_pool, request}`. `scenario_pool`은 pool 목록(`ScenarioIndexEntry`: `template_id`, `title`, `purpose`, `decision_key`)이고 원본은 모델이 `get_scenario_template(template_id)` 도구로 조회한다(호출 상한 12회). `participant_profiles[].display_name`은 서버가 바꾼 자리표시자다 | `ScenarioSet`: `{status, scenarios, clarification_questions?, message?}` |
| 답변 제출 | 작성 세션, `profile_id`, 전체 문항의 `{scenario_id, option_id, memo}` | 별도 `participant_id`와 문항별 `response_id`. 제출 후 수정 불가. |
| 생성·조기 생성 | 제출 수 도달 이벤트 또는 방장 요청 | 응답을 마감하고 채택한 제출·문항을 고정한다. 제외 안내·반영 건수는 서버가 계산한다. |
| 추천 협약서 생성 | `{participant_ids, scenarios, responses, request}` | `PactRecommendation`: `{status, positions, clauses, conditional_alternatives?, unresolved_conditions?, message?}` |
| 재생성·결과 선택 | 방장 권한, 고정 입력·결과 식별자 | 같은 입력의 두 번째 정상 결과 또는 선택한 결과. 세 번째 정상 결과 생성은 거부한다. |
| 방장 편집·이미지 저장 | 방장 권한, 선택한 결과, 조항 문구 수정 | 원본과 구분한 수정본·이미지. 이름·별명, 추천·조건부 대안·제외 안내·수정 표시를 유지한다. |
| 푸시 등록·발송 | 알림 권한·구독, 방의 완료·생성 이벤트 | 허용된 구독에만 발송하고 같은 이벤트의 중복 알림을 막는다. |
| 방 직접 삭제 | 방장 권한, 방 식별자 | 생성 중에는 거부. 호출 장부의 방 연결 해제, 나머지 방 자료 삭제 및 링크 접근 차단. |
| 푸시 상태 조회·해제 | 방장 권한 또는 해당 방 참여자 세션, 현재 기기의 endpoint | 역할·세션 등록 여부와 기기·방의 구독 존재 여부 조회. 해제 시 같은 방·endpoint 구독 전체 삭제. |
| 만료 처리 | 방 생성 시각 + 30일 | 서버 자료 삭제 및 링크 접근·작업 거부. |

### 출력 모델

필드·타입·허용값의 정본은 각 JSON Schema다. 설계 출처의 제품 기획은 이 문서 3~5절, 문항 프롬프트와 추천 프롬프트는 각 파일의 B·C절이다. 인터뷰 개념은 설계에 참고한 온톨로지 클래스이며, 출력 모델을 인터뷰에서 발견한 클래스로 세지 않는다.

| 출력 모델 | 스키마 | 설계 출처 | 설계에 사용한 인터뷰 개념 |
|---|---|---|---|
| `ScenarioSet` | [문항 스키마](../src/travel/schemas/scenario_set.schema.json) | 제품 기획, [문항 프롬프트](../src/travel/prompts/prepare_scenarios.md) | `TravelSituation` |
| `Scenario` | 문항 스키마 `Scenario` | 제품 기획, 문항 프롬프트 | `TravelSituation.trigger`·`constraints`, `Activity.name`·`place` (pool의 `scene`·`core_constraints`를 각색) |
| `ScenarioOption` | 문항 스키마 `ScenarioOption` | 제품 기획, 문항 프롬프트 | `Activity`, `ParticipantPosition` |
| `PactRecommendation` | [추천 스키마](../src/travel/schemas/pact_recommendation.schema.json) | 제품 기획, [추천 프롬프트](../src/travel/prompts/generate_pact.md) | `ParticipantPosition`, `AdjustmentOption` |
| `ResponsePosition` | 추천 스키마 `ResponsePosition` | 추천 프롬프트 | `ParticipantPosition`의 네 속성 |
| `PactClause` | 추천 스키마 `PactClause` | 제품 기획, 추천 프롬프트 | `AdjustmentOption.summary`·`participation`·`conditions`, `ParticipantPosition`, `Traveler` |
| `ConditionalAlternative` | 추천 스키마 `ConditionalAlternative` | 제품 기획, 추천 프롬프트 | `AdjustmentOption`, `ParticipantPosition` |
| `ConditionChange` | 추천 스키마 `ConditionChange` | 제품 기획, 추천 프롬프트 | `ParticipantPosition.desired_action`·`condition`·`reason` |
| `UnresolvedCondition` | 추천 스키마 `UnresolvedCondition` | 제품 기획, 추천 프롬프트 | `TravelSituation`, `ParticipantPosition` |

`status`·`message`·`clarification_questions`·`template_id`·`option_id`는 상태·식별·안내를 위한 제품 필드이며 인터뷰 어휘로 세지 않는다. `Decision`은 추천 출력에서 사용하지 않는다.

### 필드 연결과 검증 경계

- 문항 프롬프트 v9는 [문항 스키마 v2](../src/travel/schemas/scenario_set.schema.json), 추천 프롬프트 v12는 [추천 스키마 v4](../src/travel/schemas/pact_recommendation.schema.json)를 사용한다. 추천은 같은 호출에서 `ParticipantPosition`도 추출한다. 추가 LLM 호출 없이 원본·입장·조항을 대조한다.
- `profile_id`는 등록 프로필, `display_name`은 이름·별명이다. 문항 모델 입력에서는 서버가 `display_name`을 배열 순서대로 ‘친구1’, ‘친구2’…로 바꾸고 `profile_id`와 선택 정보는 그대로 둔다. 입력 검증(빈 이름 등)은 바꾸기 전 원본으로 한다. 문항의 `{{profile:profile_id}}` 표기는 코드가 조회해 본인에게 ‘당신’, 다른 사람에게 등록한 이름으로 바꾼다. 모두 같은 문항·선택지 ID와 의미를 유지하며 선택 프로필 정보를 그대로 노출하지 않는다. 표시 이름·‘당신’의 받침에 맞게 이/가·은/는·과/와를 처리한다.
- [pool 데이터](../src/travel/data/scenario_pool.json)는 `pool_version`과 `scenario_pool`을 저장한다. 모델에는 목록만 전달하고 원본은 도구 조회로 준다. 출처·작성 근거는 입력과 도구 결과에서 제외한다. 서버는 검증기에 pool 전체를 담은 검증 입력을 넘긴다. 숙박·다음 날·2박 등 장면의 적용 조건은 여행 기간과 대조해 선정한다.
- `scene`은 줄바꿈으로 나눈 개요다. 첫 줄은 상황을 한 문장으로 쓰고, 다음 줄부터 조건을 한 줄에 하나씩 쓴다. 각색해도 원본 pool의 줄 수와 순서를 유지한다.
- pool의 `decision_key`는 같은 판단을 묻는 문항의 식별자다. 각 문항에 부여한 키를 유지하고 같은 키의 문항을 함께 선정하지 않는다. 주제 자체는 중복을 금지하는 기준이 아니다.
- 코드가 문항을 확정한 뒤 `scenario_id=template_id`로 연결하고 `core_constraints`를 pool에서 조회한다. 질문 모델의 미검증 출력을 추천 모델에 바로 전달하지 않는다.
- 방 생성의 `party_size`는 2 이상 8 이하이며 자동 생성할 제출 수다(상한은 2026-11-04 팀 결정. 스파이크 평가 입력은 2~6인이었다). 문항 모델 계약의 `party_size>=1`과 제품 대상은 구분한다. 조기 생성에는 한 건 이상의 완전한 제출이 필요하다.
- `participant_id`는 채택한 제출 건의 식별자다. 같은 이름·프로필의 별도 제출도 다른 ID로 유지한다. 동일 제출 요청의 전송 재시도는 같은 건으로 처리한다. 이름 선택만으로 기존 제출의 소유권이나 수정 권한을 부여하지 않는다.
- 추천의 `participant_ids`에는 고정한 완전 제출 건만 넣는다. 미응답 등록 프로필은 모델 입력에서 제외하며 서버가 결과에 제외 안내를 붙인다. 자동 생성도 중복 이름으로 인원이 채워졌다면 반영되지 않은 등록 프로필을 안내한다. 마감과 마지막 제출·조기 생성이 겹쳐도 입력 고정과 최초 생성을 한 번만 수행한다.
- 각 제출·상황 쌍에는 정확히 한 `response_id`가 있어야 한다. `source_response_ids`는 같은 상황의 실제 응답을 참조한다. 이름·성별·나이대·MBTI는 추천 입력에서 제외하고 표시 이름은 서버가 ID로 조회한다. 추천용 장면에서도 인물 표시는 안정된 식별자로 유지한다.
- 추천 공유 문장에서 사람은 `{{participant:participant_id}}`로 표시하고, 코드는 채택 제출의 이름·별명으로 치환한다. 은/는·이/가·을/를·과/와·으로/로는 토큰 뒤의 조사 쌍을 읽어 이름의 받침으로 선택한다(ㄹ 받침은 로). 같은 이름의 제출에는 `이름(응답 1)`처럼 번호를 붙이되 조사는 이름을 기준으로 선택한다. 받침을 판별하기 어려운 영문·숫자 별명은 뒤에 ‘님’을 붙여 처리한다. 문항의 profile 토큰과 제출 건의 participant 토큰은 별도 명단으로 조회한다. 알 수 없는 ID·미해결 토큰은 표시 오류로 처리하며 화면과 저장 이미지는 같은 렌더링 함수를 사용한다. 렌더링 결과는 텍스트로 출력하고 이름에 포함된 토큰을 다시 해석하지 않는다.
- `positions[].position`은 `ParticipantPosition`의 네 속성과 일치한다. `condition`은 피로·컨디션, `desired_action`은 선택·수정 메모의 희망 행동과 제한, `reason`은 명시 이유, `expressed_content`는 실제 전달했다고 명시한 관련 발언이다. 미확정 행동은 null, 근거 없는 선택 속성은 생략한다. 후처리는 응답별 누락·중복과 인용의 원문 일치를 검사한다. 공유 결과에서는 `positions` 전체를 제외한다. 같은 모델의 추출값끼리 일치해도 의미가 맞았다고 판정하지 않는다.
- `memo`는 최대 300자의 추가 설명이며(2026-11-04 팀 결정) 동행에게 실제로 전달한 말인 `expressed_content`로 자동 변환하지 않는다. `proposed_conditions`는 새 약속, `required_changes`는 원래 조건과 제안 변경이다. 어느 것도 기존 합의·수락으로 표시하지 않는다.
- `required_changes.original_condition`은 서버가 원문과 대조하는 검증용 필드다. 공유 응답을 만들 때 이 필드·`positions`와 개인 응답 원문을 제외하고, 화면·이미지에는 `action`과 `proposed_change` 등 조율에 필요한 추천 문장만 표시한다. 표시 문장에도 메모를 그대로 인용하지 않으며, 이 기준은 방장 수정본에도 적용한다.

### 상태별 처리

| 출력 | 상태 | 사용·표시 조건 |
|---|---|---|
| `ScenarioSet` | `ready` | 6~8개와 요청 수 일치, 문항·선택지·프로필 ID, `decision_key` 중복 검사 후 사용한다. |
| `ScenarioSet` | `needs_information` | `scenarios=null`, 부족한 정보·pool을 추가 수집한다. |
| `ScenarioSet` | `unsupported`, `invalid_input` | `scenarios=null`, 지원 범위 또는 입력 수정 안내를 표시한다. |
| `PactRecommendation` | `proposed` | 원래 조건을 지키는 조항이 1개 이상이다. 모든 응답자를 고려하고 가능한 조항과 조건부 대안·미해결 사유를 구분한다. |
| `PactRecommendation` | `conditional_only` | `clauses=null`. 조건부 대안·미해결 조건·이유를 표시한다. |
| `PactRecommendation` | `needs_information` | 채택한 제출 내 응답이 누락되면 `clauses=null`, `positions=[]`와 안내를 반환한다. 응답은 모두 있지만 정보 부족으로 조항·대안이 없으면 응답별 `positions`와 `unresolved_conditions`·안내를 반환한다. 제외된 등록 명단의 미응답 때문에 이 상태로 바꾸지 않는다. |
| `PactRecommendation` | `unresolved` | 정보는 충분하지만 검토한 방식에서 안을 찾지 못했다. 조건부 대안도 없으며 막힌 조건을 설명한다. |
| `PactRecommendation` | `unsupported`, `invalid_input` | `clauses=null`, 지원 범위 또는 입력 오류를 안내한다. |

상태에 필요한 배열·문자열은 비어 있으면 안 된다. 입력 오류·지원 밖·채택된 제출 내 누락 검사 후 일반 조항이 있으면 `proposed`, 조건부 대안만 있으면 `conditional_only`, 둘 다 없고 정보가 부족하면 `needs_information`, 충분해도 안을 찾지 못하면 `unresolved`이다. 상세 후처리는 두 프롬프트 B절을 따른다.

JSON·스키마·상태 조합 오류는 이유를 붙여 최대 1회 재요청하고 다시 실패한 결과는 사용하지 않는다. 호출 실패는 실행 오류로 알리며 정상 결과 재생성 횟수에 포함하지 않는다. 실패 상태에서 재시도를 요청해도 같은 고정 입력을 사용한다. 고정 유머 문구 “너네 조합 꽝이니 여행 가지 마세요!”는 `unresolved` 화면에서만 표시하고, 바로 옆에 “이번 응답 조건에서는 추천안을 찾지 못했습니다.”와 실제 막힌 조건을 함께 표시한다. 결과의 판단 대상은 이번 응답 조건이며, 사람의 성격·궁합 점수나 여행 실패 판정으로 저장·표시하지 않는다. 정보 부족·제출 누락·호출 오류와 다른 상태에 이 문구를 노출하거나 설명을 빠뜨리면 AC7 실패이다.

## 6. 수용 기준

EARS 문형으로 조건·서비스·동작을 명시한다. 케이스 ID는 구현 단계 골든 테스트의 식별자이다. 아래 표는 제품의 완료 기준이며 이번 모델 출력 검사 범위와 구분한다.

| AC | 요구사항 | 케이스·판정 방법 |
|---|---|---|
| AC1 [이벤트 기반] | 유효한 문항 요청이 오면, 서비스는 요청한 6~8개를 반환하고 문항·선택지 ID와 핵심 제약·선택 의미를 보존하며, 인원을 쓰면 본인을 포함한 총인원으로 표시한다. | `scenario_contract`: 기간·인원에 맞지 않는 문항을 제외한 뒤 선정 수와 `decision_key` 중복을 대조한다. 핵심 조건을 바꿔 부적합 문항을 끼워 넣으면 실패이다. 주제 고정 비중은 없으며 같은 주제·다른 고민은 함께 선정할 수 있다. |
| AC2 [예외 대응] | 필수 여행 정보·프로필 또는 여행 조건에 맞는 서로 다른 판단의 pool이 부족하면, 서비스는 `needs_information`으로 필요한 정보를 요청한다. 범위 위반은 `invalid_input`, 지원 밖 요청은 `unsupported`로 반환한다. | `scenario_input`: 기본 다섯 유형과 프로필 누락·수 불일치·중복 ID·선택 정보 생략을 검사한다. |
| AC3 [상시 적용] | 서비스는 다른 참여자에게 개인 선택·메모 원문, `positions`, `original_condition`, 선택 프로필 정보를 반환하지 않는다. | `response_privacy`: 제출 전에 원문 비공개와 바람·한계의 이름 포함 결과 반영 안내가 표시되는지 확인한다. 응답 조회와 공유 결과에서 원문·검증용 인용 필드가 제외되고, 공개 문장은 두 층으로 판정한다. 코드 검사는 메모의 연속 15자 이상(공백·문장부호 포함)이 그대로 나오면 실패이며, 같은 부분이 문항의 장면·질문·선택지 문구에도 있으면 제외한다. 의미 판정은 조율에 필요한 바람·한계 외의 개인 사정·타인 평가·감정 표현이 나오면 실패이다. 두 기준은 모델 출력과 방장 수정본에 같이 적용한다. 이름 재선택·다른 응답 ID 조회에도 같은 기준을 적용한다. 조율 조건의 의미와 적용 대상 이름은 표시할 수 있다. |
| AC4 [이벤트 기반] | 유효한 제출 수가 설정 인원에 도달하거나 방장이 조기 생성을 요청하면, 서비스는 입력을 한 번 고정하고 응답을 마감해 생성한다. | `response_closure`: 같은 이름의 별도 제출을 각각 집계한다. 조기 생성 0건은 거부하고 1건 이상은 허용한다. 동시 제출·조기 요청에서도 최초 생성은 한 번이며 이후 제출·수정은 거부한다. 제외 안내와 반영 건수를 검사한다. |
| AC5 [상시 적용] | 서비스는 같은 상황의 실제 응답만 근거로 사용하고 잘못된 ID·중복 응답 ID를 거부한다. | `evidence_integrity`: 같은 이름·서로 다른 제출 ID는 허용하고, 같은 제출·상황의 중복은 `invalid_input`으로 처리한다. 작성자·상황 연결을 대조한다. |
| AC6 [이벤트 기반] | 추천 요청이 오면, 서비스는 명시적 요구·한계와 선택을 수정한 메모를 보존하며 모든 응답자를 조율에 포함한다. 모호한 내용은 미확정으로 남긴다. | `memo_limits`: 같은 선택·다른 메모, 소수 한계, 타인 추측, 중복 이름의 다른 답변을 대조한다. 일부 활동 참여는 허용하지만 충돌하는 사람을 조율 대상에서 빼거나 미확정 동의·행동을 전제로 하면 실패이다. |
| AC7 [상시 적용] | 서비스는 새 약속을 `proposed_conditions`로 구분하고 가상 사실·추천을 실제 일정·전원 합의·성격·궁합 판정으로 표시하지 않는다. | `proposal_boundary`: 일반 조항과 조건부 대안은 미래의 유사 상황에서 사용할 협약으로 쓴다. 가상 장면의 목적지·활동·금액·시각을 확정하는 해결책이나 시간표이면 실패이다. 가상 숫자·예약·재합류 제안과 출력 표현을 대조한다. 등록 프로필을 답변 근거로 사용하지 않는지 검사한다. 유머 문구는 [상태별 처리](#상태별-처리)의 조건으로만 표시하며, 궁합 점수·여행 실패 판정으로 확장하면 실패이다. |
| AC8 [복합 조건] | 원래 바람·조건을 모두 지키는 조율이 어려우면 조건부 대안을 검토한다. 변경이 필요한 대안을 제시하면, 서비스는 원문 조건·응답 근거를 서버에서 검증하고 사용자에게 변경 제안을 조건부 대안으로 표시한다. 그런 대안만 있으면 `conditional_only`로 반환한다. | `conditional_result`: R12처럼 메모를 인용한 `original_condition`은 서버에 유지하고 공유본에서 제외한다. 메모 우선 적용, `clauses=null`, 변경 제안과 수락의 구분을 검사한다. 의미는 [공통 판정 규칙](spikes/grounded_pact.md#핵심-조율-품질의-별도-평가)으로 판정한다. 원래 조건을 지키는 일반 조항이 가능한데 조건부 대안만 내거나(H08), 변경 제안이 응답의 바람을 필요 이상 줄이면(H06) 실패이다. R12·H05는 통과 사례다. |
| AC9 [예외 대응] | 정보가 충분해도 검토한 방식에서 안을 찾지 못하면, 서비스는 `unresolved`와 막힌 조건을 반환한다. | `result_routing`: 부분 조항·조건부 대안·전체 정보 부족·전체 미해결·호출 오류를 나눠 상태 우선순위와 유머 표시를 검사한다. 막힌 조건은 함께 행동·시간 나누기·별도 행동이 막힌 이유를 응답자의 한계와 연결해 설명한다. 정보 부족을 `unresolved`로 내거나(E02 대조) 충돌을 정보 부족으로 내면 실패이다. E03은 통과 사례다. |
| AC10 [예외 대응] | 출력 형식 검사가 실패하면, 서비스는 이유를 붙여 최대 1회 재요청하고 다시 실패한 출력을 사용하지 않는다. | `output_validation`: JSON 절단·추가 키·잘못된 상태를 주입해 재요청 횟수, 결과 미사용, 정상 결과 재생성 횟수 미소비를 검사한다. |
| AC11 [예외 대응] | 프로필·여행 정보·pool·메모에 규칙 변경 지시가 있으면, 서비스는 이를 명령으로 실행하지 않고 출력 계약을 유지한다. | `untrusted_input`: 조작 지시 유무의 쌍에서 허위 동의·한계 무시·임의 필드·지시 유출이 없는지 검사한다. |
| AC12 [이벤트 기반] | 결과 수정 요청이 오면, 서비스는 별도 방장 권한과 조항 문구만 변경했는지 확인하고 원본과 구분된 수정본을 저장한다. | `host_edit`: 방장 이름 선택만 한 요청은 거부한다. 추가·삭제·근거·적용 대상 변경을 막고 원본·수정 표시를 확인한다. |
| AC13 [이벤트 기반] | 이미지 저장 요청이 오면, 서비스는 미리보기와 같은 이름·별명, 추천·조건부 대안·제외 안내·초안·수정 표시를 포함한 이미지를 만든다. | `result_export`: AC3의 공개 기준을 원본·방장 수정본에 적용한다. `original_condition` 없이 변경 제안이 표시되는지, 같은 이름의 제출 구분과 화면·이미지가 일치하는지 검사한다. 참여자 토큰의 이름 치환과 조사 5쌍을 받침 유무·ㄹ 받침·중복 이름·영문/숫자 별명으로 검사하고, 없는 ID·남은 토큰은 표시를 막는다. |
| AC14 [상시 적용] | 서비스는 아이폰 Safari와 안드로이드 Chrome에서 응답·생성·편집·저장 흐름을 읽고 조작할 수 있게 하고 오류를 텍스트로 표시한다. | `mobile_access`: 두 실제 기기의 모델·OS·브라우저 버전을 기록하고 화면 잘림·포커스·레이블·이미지 저장·푸시 허용 및 거부 흐름을 확인한다. 두 기기에서 응답·생성·편집·저장 8건이 모두 통과하고 막힘이 0건이면 합격이다. 막힘은 화면 잘림으로 조작할 수 없음, 포커스 이동 불가, 레이블 없는 입력, 이미지 저장 실패, 텍스트로 표시되지 않는 오류이다. 푸시 흐름도 같은 기준으로 보되 아이폰은 화면 확인 흐름으로 대신하고, 그 밖의 어긋남은 기록만 한다. |
| AC15 [이벤트 기반] | 프로필을 이용해 문항을 표시하면, 서비스는 본인을 ‘당신’, 다른 동행을 등록한 이름·별명으로 바꾸고 모든 뷰의 상황·선택 의미를 유지한다. | `profile_rendering`: 선택 정보 유무와 이름 변경에 따른 뷰를 비교한다. 받침이 있는 이름·없는 이름·‘당신’에 이/가·은/는·과/와를 적용하고, 개발용 단순 치환에서 나온 ‘당신가·당신는·당신와’를 재현해 올바른 조사와 의미 보존을 확인한다. 성별·나이대·MBTI 노출과 선호·한계 추정, 없는 프로필 토큰을 거부한다. |
| AC16 [이벤트 기반] | 이미 제출된 이름을 선택하면, 서비스는 선택란 아래에 빨간 안내 문구를 표시하고 새 응답 작성을 허용한다. | `duplicate_name`: 같은 이름의 두 제출은 별도 ID로 저장한다. 전송 재시도는 동일 건으로 처리하고, 기존 제출 열람·수정은 허용하지 않는다. |
| AC17 [이벤트 기반] | 방장이 정상 결과 재생성을 요청하면, 서비스는 고정 입력으로 한 번 더 생성하고 두 결과 중 하나를 선택하게 한다. | `regeneration`: 입력 불변·두 결과 보존·선택·세 번째 정상 생성 거부를 검사한다. 재생성 결과가 선택 전까지 방장에게만 보이고 기존 공개 결과가 유지되는지 검사한다. 실패 재시도는 재생성 횟수를 소비하지 않는다. |
| AC18 [이벤트 기반] | 응답 완료·협약서 생성·방장의 첫 결과 선택 이벤트가 발생하면, 서비스는 권한을 허용한 해당 구독에 푸시를 보낸다. | `push_events`: 거부자에게 미발송, 방장 완료·생성 통지, 참여자는 첫 결과 선택 때만 통지(초안 생성 때 미발송), 자동 생성 성공 시 방장 알림 한 번, 이벤트 재처리 시 중복 방지, 실패 후 성공 알림을 검사한다. 기기·방별 해제, 다른 기기·방 유지, 반복 해제·재등록, 해제된 대기 알림 제외, 발송 전 DB 오류 시 미발송 유지, 상태 조회 실패와 서비스 워커 대기 시간 초과의 재시도 표시를 검사한다. |
| AC19 [상태 기반] | 방 생성 후 30일이 지나면, 서비스는 방 관련 서버 자료를 삭제하고 초대 링크 조회·제출·재생성·푸시를 거부한다. | `retention`: 만료 직전·정각·이후와 편집·재생성 후를 검사한다. 서버 자료는 삭제되고 기기에 저장한 이미지는 유지되는지 확인한다. |
| AC20 [이벤트 기반] | 방장이 직접 삭제를 확인하면, 서비스는 생성 중인 방을 제외하고 호출 장부의 방 연결을 해제한 뒤 나머지 방 자료를 삭제한다. | `room_delete`: 방장 외 거부, 생성 중 거부, 방 자료 삭제와 호출 장부 연결 해제, 삭제 후 일일 비용 한도 유지, 링크 접근 차단, 삭제 실패 시 DB 롤백과 기기 정보 보존을 검사한다. |

AC6~AC9의 자동 발급 채택 조건은 [스파이크](spikes/grounded_pact.md)에서 사전에 정한 평가 세트의 80% 이상 통과와 허위 동의·명시적 한계 위반·원문 왜곡 0건이다. 구조 검사만 통과한 건은 최종 통과로 세지 않는다. 통과는 고정한 평가 세트에서 금지 오류가 나오지 않았고 채택 기준을 충족했다는 뜻이며, 이후 모든 출력의 무오류를 보장하지 않는다. 평가한 모델·프롬프트·pool·스키마 조합을 기록하고 조합이 바뀌면 다시 평가한다. 실제 참여자에게 공개할 조합의 판정은 공개 전에 끝낸다. 여기서 실제 참여자는 실제 여행 그룹이다. 2026-11-11~18 동료 평가는 가상 입력으로 하는 체험이라 품질 판정 전에 공개하고, 실제 여행 그룹은 사람 판정 뒤에 받는다(2026-11-07 팀 결정). 명확한 요구를 근거 없이 제외하거나 한계를 무시한 일부안을 만들면 건별 실패이다. 전체 정보 부족·전체 미해결·인젝션·호출 오류와 신규 운영 정책의 AC는 별도로 검증한다.

### 서비스 API 검증

Sol 서비스 API는 [문항 스키마 v2](../src/travel/prompts/prepare_scenarios.md#b-스키마-규칙)와 추천 스키마 v4를 `text.format`의 `strict: false`로 수용한다(2026-11-05 확인, [스파이크](spikes/scenario_tool_call.md)). 방 500건의 전체 흐름을 기준으로 캐시·추론 토큰·실패 재시도·정상 결과 재생성을 포함해 예산을 확인한다. 총 크레딧 예산은 $100이고 방당 상한은 $0.20이다(2026-11-04 팀 결정). 2026-11-05 실제 호출 10회 측정에서 방당 비용은 $0.045~$0.123(평균 $0.083)였다([서비스 위임 기록 §2-4](prompts/delegation_service.md)). 평가·개발 호출도 같은 예산을 쓴다. 배분은 서비스 $45, 7강 평가 $25, 개발·회귀·리허설 $15, 예비 $15이며 측정 뒤 다시 나눌 수 있다(2026-11-05 팀 결정). 모델 출력 검사 결과를 API 연동·비용·지연의 측정값으로 사용하지 않는다.

운영 계약은 위 AC의 케이스 ID에 맞춰 구현 설계와 골든 케이스에 반영한다. 방장 권한, 제출 건별 식별, 마감·동시 요청, 재생성·실패 재시도, 푸시 중복 방지와 만료 삭제를 포함한다. 실제 기기의 전체 흐름은 AC14, 문항의 이름·조사는 AC15, 추천 화면·이미지의 이름·조사는 AC13으로 검증한다.

### 제품 사용 검증

품질 기준을 충족한 추천을 실제 여행 그룹(친구·연인·가족)이 사용하는 모습을 관찰해 [PROBLEM의 해결 가설과 행동 지표](PROBLEM.md#해결-가설)를 확인한다. 추천 활용률은 출발 전 결과 확인 세션에서 진행자가 그룹이 고른 조항·적용 대상·선택 이유를 기록해 측정하며, 여행 중 행동은 관찰하지 않는다(2026-11-04 팀 결정). 관찰 전에 대상 그룹의 조건·수, 관찰 시간, 추천 활용률의 목표·기각 비율을 정하고 기록한다. 참가자는 실제 사람 단위로 확인하며 같은 이름의 여러 제출을 여러 사람으로 세지 않는다.

최종 목표는 사전 확정한 출발 전 여행 그룹 5개 중 활용 성공 3개 이상(정량)과 정성 목표 달성 3개 이상(정성)이다(2026-11-05 팀 결정). 분모는 사전 확정한 5개이며(모집 마감일까지 못 채우면 확정한 수 N과 그 60% 이상, N이 3 미만이면 판정하지 않음), 결과는 활용 성공·활용 실패·품질 실패·관찰 중단으로 나눠 기록한다. 성공 기준, 진행 질문, 기록 항목, 판정 방법은 [관찰 절차](research/observation_protocol.md)를 따른다. 탐색적 목표라 일반 여행자의 활용률이나 효과로 넓혀 해석하지 않는다.

활용 성공·실패와 품질 오류·관찰 중단의 구분은 [PROBLEM의 해결 가설](PROBLEM.md#해결-가설)을 따른다. 결과 조회·이미지 저장을 전원 동의나 실제 여행의 갈등 감소로 해석하지 않으며, 이 관찰은 모델 출력 품질 실험의 결과에 포함하지 않는다.
