# 강의 5 산출물 작성: A. 위임 대상 선정, B. 골든 케이스, C. 테스트 하니스 위임

[강의 5 작성지침](../../references/course/05/강의05_위임검증_골든테스트_작성지침.md)의 A절, B절, C절 "우리 팀" 칸을 채운 문서다. C절은 결함 주입과 로더 확인까지 실행해 기록했고(git을 이용한 원복 확인은 남음), D절(기능 위임) 이후는 아직 진행하지 않았다.

작성 경위: AI(Claude)가 SPEC, AGENTS.md, 추천 프롬프트 v11, 스파이크 기록을 바탕으로 초안을 썼다. 팀 검토 전이며, 판정 기준은 아래 "팀 확인이 필요한 해석"을 포함해 팀이 확정한다.

---

## A. 위임 대상 선정

- **첫 위임 기능(경계 분명, 테스트로 명세 가능)**: `src/travel/pact.py`의 `validate_pact_output(pact_input, raw_output)`. 모델이 낸 `PactRecommendation`을 공유하기 전에 검사해 `{valid, errors[{code, path, detail}]}`를 반환한다. 검사 대상은 JSON 형식과 스키마, 상태별 필드 조합, 응답 누락 처리, 근거 연결, 입장 추출과 원문 인용, 응답 연결, 공유 문장의 참여자 토큰과 조사다.
- **직접 담당할 것(아키텍처, 판단 기준)**:
  - 무엇을 오류로 볼지: 오류 코드 12개와 각 판정 규칙
  - 상태별 필수·금지 필드 조합: [추천 프롬프트](../../src/travel/prompts/generate_pact.md) B절의 상태별 후처리 규칙
  - 원문 인용으로 인정하는 범위: 해당 응답의 메모 또는 고른 선택지 문구의 정확한 발췌
  - 검사 범위의 경계: 조율 내용의 품질(요구 보존이 맞는지, 제안이 적절한지)은 검사하지 않고 사람 평가와 강의 7 evals에 맡긴다
  - 검증 실패 뒤의 처리: 이유를 붙인 1회 재요청 후 미사용(AC10). 검증기가 아니라 workflow가 맡는다
- **위임한 이유 / 직접 담당한 이유**:
  - 위임한 이유: 입력(고정 입력, 모델 출력 문자열)과 출력(통과 여부, 오류 코드)이 명확하고, 같은 입력이면 결과가 항상 같다. [v11 회귀 점검](../spikes/grounded_pact.md#기술-점검-현황)의 실제 출력과 결함을 넣은 출력으로 정답을 데이터로 만들 수 있다. 범위는 파일 하나, 함수 하나다.
  - 직접 담당한 이유: 무엇을 오류로 볼지는 근거 없는 조항, 응답자 누락, 유머 문구 노출을 막겠다는 제품 정책이고 SPEC의 AC를 해석하는 일이다. 이 기준을 AI가 정하면 그 기준으로 AI의 구현을 검증할 수 없다.

선택 근거: 이 기능은 모델 출력이 공유되기 전의 마지막 관문이다. [스파이크](../spikes/grounded_pact.md#1-가장-위험한-가정)가 꼽은 가장 큰 위험인 "응답 조건을 왜곡한 추천"을 코드로 막는 첫 장치이며, 걸린 AC(AC4~AC10, AC13)가 가장 많다. 규칙은 프롬프트 B절과 "필드와 함수 인자" 절에 이미 정해져 있어 새 판단을 만들지 않고 데이터로 옮길 수 있다. 약점은 함수는 하나지만 규칙이 12개라 지침이 권하는 작은 범위보다 크다는 점이다. 더 작은 대안은 이름·조사 렌더러(`render_participant_names`, AC13·AC15)였다.

## B. 골든 케이스

전체 파일: [`tests/harness/golden_cases.yaml`](../../tests/harness/golden_cases.yaml) (케이스 25개). fixture: [`tests/harness/fixtures/pact/`](../../tests/harness/fixtures/pact/) (10개).

### 케이스 형식 (발췌)

```yaml
error_codes: [json_invalid, schema_violation, status_combination, input_status_mismatch, unknown_reference, evidence_mismatch, positions_mismatch, quote_mismatch, unlinked_response, token_invalid, particle_pair, humor_text]

cases:
  - name: p1_proposed_valid
    fixture: p1_proposed
    expect_valid: true
    note: >-
      정상. 세 사람의 응답을 모두 근거로 한 일반 조항 하나. 참조·근거 작성자·positions·조사 쌍이 모두 맞다.
      잘못된 검증기가 정상 출력을 거부하지 않는지 확인한다. (AC5, AC6)

  - name: fabricated_response_id
    fixture: p1_proposed
    patch:
      - {op: add, path: /output/clauses/0/source_response_ids/-, value: rZ}
    expect_valid: false
    must_include_errors: [unknown_reference]
    note: >-
      금지 행동. 입력에 없는 응답 rZ를 근거로 인용했다. 실제 응답만 근거로 써야 한다. (AC5)

  - name: e01_fixed_particle_real
    fixture: e01_multi_fixed_particle
    expect_valid: false
    must_include_errors: [particle_pair]
    must_not_include_errors: [quote_mismatch, evidence_mismatch, unknown_reference, unlinked_response, positions_mismatch, status_combination]
    note: >-
      금지 행동, 실제 모델 실패. "{{participant:sub_10}}이 모든 활동을"처럼 이/가 쌍 대신 한쪽 조사만 붙었다. (AC13, AC8)
```

입력 키:
- `fixture`: `tests/harness/fixtures/pact/<이름>.json`의 `{source, input, output}`
- `patch`: fixture에 적용할 RFC 6902 연산(add, remove, replace). 경로는 `/input/...` 또는 `/output/...`
- `raw_output`: 있으면 output 대신 이 문자열을 그대로 넘긴다. JSON 파싱 전 단계 검사용이다.

`pact_input`은 [SPEC 5절](../SPEC.md#5-인터페이스) 추천 생성 입력 `{participant_ids, scenarios, responses, request}`와 같은 모양이다. 출력은 [추천 스키마 v4](../../src/travel/schemas/pact_recommendation.schema.json)의 `PactRecommendation`이다.

### 케이스 구성과 검사 범위

- **정상 케이스**(4개, 통과해야 함): `p1_proposed_valid`, `p3_partial_with_exclusion_valid`, `r12_conditional_only_valid`, `e03_unresolved_valid`
- **경계 케이스**(5개, 통과해야 함): `p2_missing_response_valid`(응답 누락), `e02_all_unclear_valid`(6문항·응답 18개·메모 전부 null), `p4_invalid_input_valid`, `p5_unsupported_valid`, `single_submission_valid`(조기 생성으로 채택 1건)
- **금지 행동 검증 케이스**(16개, 거부해야 함):
  - 실제 모델 실패: `e01_fixed_particle_real`
  - 형식: `truncated_json`, `extra_key_rejected`, `agreed_status_rejected`
  - 상태 조합: `unresolved_with_clauses`, `unresolved_with_conditional_alternative`
  - 응답 누락 무시: `missing_response_but_proposed`
  - 근거: `fabricated_response_id`, `cross_scenario_evidence`, `obligation_on_excluded_participant`
  - 입장 추출·인용: `position_missing`, `invented_condition`, `original_condition_not_quoted`
  - 응답자 누락: `excluded_response_dropped`
  - 공유 문장: `unknown_participant_token`, `humor_in_model_output`

- **각 케이스 ↔ 대응 AC 번호**:
  - AC4: `p2_missing_response_valid`, `single_submission_valid`, `missing_response_but_proposed`
  - AC5: `p1_proposed_valid`, `p4_invalid_input_valid`, `fabricated_response_id`, `cross_scenario_evidence`, `position_missing`
  - AC6: `p1_proposed_valid`, `p3_partial_with_exclusion_valid`, `obligation_on_excluded_participant`, `invented_condition`, `excluded_response_dropped`, `unknown_participant_token`
  - AC7: `p5_unsupported_valid`, `agreed_status_rejected`, `humor_in_model_output`
  - AC8: `r12_conditional_only_valid`, `e01_fixed_particle_real`, `original_condition_not_quoted`
  - AC9: `p3_partial_with_exclusion_valid`, `e03_unresolved_valid`, `p2_missing_response_valid`, `e02_all_unclear_valid`, `unresolved_with_clauses`, `unresolved_with_conditional_alternative`
  - AC10: `truncated_json`, `extra_key_rejected`, `agreed_status_rejected`
  - AC11(구조적 영향만): `extra_key_rejected`
  - AC13: `e01_fixed_particle_real`, `unknown_participant_token`

- **판정 키 목록과 각 키의 검사 범위**:
  - `expect_valid`: 결과의 `valid` 값. 모든 케이스의 필수 키다.
  - `must_include_errors`: 결과 `errors`의 `code` 전체 집합에 모두 포함돼야 한다. `expect_valid: false`면 필수다. 불통과가 엉뚱한 이유로 나온 경우를 실패로 만든다.
  - `must_not_include_errors`: 결과 `errors`의 `code` 전체 집합에 하나도 없어야 한다. 정상 부분을 오류로 잘못 잡는지 검사한다.
  - 검사하지 않는 범위: 오류의 `path`, `detail`, 개수와 순서. 한 결함에서 관련 오류가 함께 나오는 것은 허용한다. 예를 들어 `missing_response_but_proposed`에서는 `unknown_reference`, `evidence_mismatch`도 함께 나온다.
  - 오류 코드 12개의 정의는 YAML 머리말에 있고, 허용 목록은 `error_codes` 키에 있다.

- **정답 후보와 오답 후보**: 출력이 목록이 아니라 판정이므로, 같은 fixture에서 맞는 출력과 결함 하나만 넣은 출력을 짝으로 두었다. 결함 외의 차이가 없어 해당 규칙이 빠지면 그 케이스만 실패한다.
  - `p1_proposed`: 정상 1개, 결함 8개(형식 3개, 근거, 입장 누락, 컨디션 지어내기, 응답 누락, 토큰)
  - `p3_partial`: 정상 1개, 결함 3개(상태, 적용 대상, 응답자 누락)
  - `r12_conditional_only`: 정상 1개, 결함 1개(원문 인용)
  - `e03_unresolved`: 정상 1개, 결함 2개(대안 혼입, 유머 문구)
  - `e02_all_unclear`: 정상 1개, 결함 1개(다른 문항 근거)
  - `e01_fixed_particle_real`: 한 출력 안에서 조사 오류는 잡고 나머지 정상 부분은 오류로 잡지 않는지 `must_not_include_errors`로 함께 본다.

- **fixture의 경로와 기준 버전(커밋)**:
  - 경로: `tests/harness/fixtures/pact/*.json`
  - 실제 출력 9개: [`docs/spikes/grounded_pact_v11_regression_outputs.jsonl`](../spikes/grounded_pact_v11_regression_outputs.jsonl)의 `run_id: v11-regression-20261007`에서 P1~P5, E01~E03, R12를 옮겼다. 설정은 `gpt-6.1-sol`, 추론 `low`, 추천 프롬프트 v11, 스키마 v4다. 저장소 기준 커밋은 `f699469`다. 각 파일의 `source`에 `case_id`, `run_id`, `output_sha256`, 당시 자동 검사 결과를 기록했다. `output_sha256`은 원본 출력 파일의 해시라서 fixture를 다시 직렬화한 값과 다를 수 있다.
  - 수기 작성 1개: `single_submission.json`. 모델 출력이 아니며 `source.note`에 표시했다.
  - 같은 설정으로 한 번 더 실행한 두 번째 회차 출력 9개와 사람 평가 12건(H01~H12)에 같은 규칙을 적용해 보았다. 결과는 스파이크 자동 검사와 일치했다. E01만 조사 오류로 걸렸고, 사람 평가에서 실패한 H06·H08은 구조가 맞아 통과했다. 이 검증기가 내용 품질을 판정하지 않는다는 범위 경계를 보여 준다.

- **아직 다루지 못한 필수 AC와 보완할 케이스**:
  - AC3: 공유 문장에 메모 원문이 그대로 인용됐는지는 판정 기준(몇 글자 이상 같으면 인용으로 볼지)이 없어 케이스를 만들지 않았다. 기준을 정한 뒤 이 검증기 또는 공유본 생성(`build_shared_recommendation`)의 케이스로 보완한다.
  - 공유 문장에 토큰 없이 맨 participant ID를 쓴 경우는 ID가 짧은 문자열(A, B)이라 오탐 없이 판정하기 어려워 검사하지 않는다.
  - AC11: 입력 속 지시문의 영향 중 구조적 결과(스키마 밖 키, enum 밖 status)만 다룬다. 허위 동의나 한계 무시 같은 내용상 영향은 evals에서 본다.
  - AC6, AC8의 의미 보존(요구가 맞게 반영됐는지)은 이 검증기의 범위 밖이며 [사람 평가 기준](../spikes/grounded_pact.md#핵심-조율-품질의-별도-평가)과 강의 7 evals가 맡는다.
  - 입력 자체의 오류(중복 응답 ID, 없는 선택지)를 생성 전에 거르는 일은 `validate_submission_responses`의 몫이다. 이 검증기는 모델이 `invalid_input`을 냈을 때 그 상태 조합만 본다.
  - 다른 기능의 AC(AC1, AC2, AC12, AC14~AC19)는 해당 기능을 위임할 때 별도 케이스로 만든다.

- **팀 확인이 필요한 해석**: 아래 규칙은 SPEC과 프롬프트에서 해석해 정했다. 팀이 확정하거나 수정한다.
  - 채택 제출 건 안의 응답 누락은 `needs_information`이면서 `positions=[]`일 때만 맞는 결과로 본다. 누락이 없는데 이 조합이면 오류다.
  - 조사 검사는 프롬프트가 지정한 5쌍(은/는, 이/가, 을/를, 과/와, 으로/로)만 본다. `이랑/랑`처럼 목록에 없는 조사는 검사하지 않는다.
  - `original_condition`은 메모뿐 아니라 고른 선택지 문구의 정확한 발췌도 인정한다. 프롬프트 C절 "선택한 선택지 문구 또는 메모에서 정확히 인용"을 근거로 했다.
  - JSON 파싱 실패나 스키마 위반이 나오면 이후 규칙은 검사하지 않는다. `invalid_input`, `unsupported`에서는 근거·입장·연결 규칙을 검사하지 않는다.

## C. 테스트 하니스 위임

위임 프롬프트와 확인 계획, 결함별 기대 결과는 실행 전에 확정했다. 결과 칸은 실제로 실행한 결과로만 채웠고, 아직 하지 않은 확인은 "(미실행)"으로 남겼다.

### 실행 전 준비

- **구현 환경**: Python, pytest. 필요한 라이브러리는 pytest, PyYAML, jsonschema다. `src/travel/pact.py`를 `travel.pact`로 불러오도록 `pyproject.toml`의 pytest 설정에 `pythonpath = ["src"]`를 둔다.
- **에이전트 하니스(G절)를 위임 전에 갖춘다**:
  - `CLAUDE.md`의 `@AGENTS.md` 로드를 새 세션에서 `/context`로 확인한다.
  - `.claude/settings.json`에서 `pytest` 실행은 허용하고 `git push`는 확인 대상으로 둔다.
  - AGENTS.md 4절 금지 사항에 판정 기준 보호 문장을 반영한다(아래 "수정 금지 문장" 참고).
- **체크포인트**: 위임 직전 상태를 커밋해 둔다. 결함 주입 뒤 이 커밋과 비교해 원복을 확인한다.

### 테스트 하니스 위임 프롬프트

실제로 붙여 넣은 원본은 `docs/prompts/delegation_pact_validation.md` §1-1에도 그대로 보존한다.

```text
tests/test_pact_validation_golden.py 를 만들어줘.
- 목표: tests/harness/golden_cases.yaml 을 읽어 케이스마다 하나씩 도는 테스트.
  대상 함수는 src/travel/pact.py 의 validate_pact_output(pact_input, raw_output) 이고 {valid, errors[{code, path, detail}]} 를 반환한다.
- 케이스를 코드에 복사하지 말 것. YAML에서 읽고, 케이스 name을 테스트 id로 쓴다.
- 입력 준비: tests/harness/fixtures/pact/<fixture>.json 을 읽어 깊은 복사본에 patch(RFC 6902의 add, remove, replace, 경로는 /input/... 또는 /output/...)를 순서대로 적용한다.
  raw_output 이 있으면 그 문자열을, 없으면 output 을 JSON 문자열로 직렬화해 넘긴다. pact_input 은 문서의 input 이다.
- 검사 항목: 케이스에 있는 키만 검사한다.
  expect_valid → result.valid 와 같음 / must_include_errors → 모두 errors의 code에 있음 / must_not_include_errors → 하나도 없음
- 로더 검사(구현 여부와 무관하게 항상 실행):
```
